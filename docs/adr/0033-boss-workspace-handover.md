# ADR-0033：boss 工作区交接

- 状态：已接受
- 日期：2026-10-28
- 修订：2026-11-01，见文末「修订：只有 boss 的工作区与接手 Skill」。
- 修订 [ADR-0017](0017-manager-chat-session-identity.md) 的“记录永远归原 boss”与“磁盘只存归属哈希”；扩展 [ADR-0026](0026-sqlite-conversation-store.md) 的表。

## 背景

ADR-0017 让每条记录永远归创建它的 boss 聊天：另一个聊天续接节目或私聊记录时报 “belongs to a different manager session”。boss 额度用完、无法再调用工具，或用户想换一个更合适的 Agent 时，工作区里的会议组和工位因此无法再用，只能在新聊天里从头开。

## 决定

- 工作区（同一 `manager_session` 键下的全部会话）可以标记为「待接手」，被另一个 boss 认领后整体归新 boss。会话行的 `manager_session` 不改写，它从此只表示工作区；`workspaces` 表记录每个工作区现在由哪个 boss 键写入（`owner`）。没有行的工作区归创建它的 boss，与 ADR-0017 相同。
- 服务按调用方的 boss 键解析工作区：它拥有某个工作区就用那个工作区；它原来的工作区已交给别人且自己没有新工作区时，写入类调用（`start_agent`、`run_round`、交接）拒绝，提示已交给哪个宿主的 boss；其余情况就是它自己的键。新 boss 新建的会话也存进原工作区，App 里仍是同一个工作区，只显示 boss 已更换。
- 新增工具 `handover`，`list` 不变：老 boss 带 `release=true`（可附交接说明）把自己的工作区标为待接手；不带参数列出待接手的工作区；带 `workspace_id` 认领。认领要求该工作区待接手，且新 boss 名下没有其他有会话的工作区；认领自己的待接手工作区即撤回交接。认领回执给出交接说明、各会话的 ID、标题与运行状态（用 `read_conversation` 回读），以及老 boss 的原生会话文件路径（有时）。B 交回 A 或交给 C 用同一套机制。
- 交接说明的写法写在工具参数说明里，不依赖其他 Skill：按新 boss 下一步的重点写，带交接原因和建议加载的 Skill；会话、PR、ADR 等已有材料只给出处，席位回答由新 boss 自己回读；不含密钥和敏感个人信息，因为它存进数据库并在 App 显示。老 boss 写不了说明时，由会话文件路径和工作区历史兜底。
- AgentNave 不启动新 boss。新 boss 由用户在任意宿主里开新聊天；只有用户要求接手或交接时，boss 才调用这个工具，不在每个新聊天里主动查。
- 交接时仍在运行的任务和轮次留在老 boss 的服务进程里跑完，结果照常落进历史；不做跨进程 `wait`。新 boss 用 `read_conversation` 读结果，工位空闲、会话锁释放后按现有 `writable` 机制续用。
- 托盘在工作区右键菜单提供「交给其他 boss 接手」，只有确认按钮、没有输入框，用于老 boss 已无法调用工具的情况；工作区列表显示待接手和 boss 已更换。
- `workspaces` 表用 `CREATE TABLE IF NOT EXISTS` 加进现有库，`user_version` 仍为 1：旧服务和旧托盘不读它，照常工作，只是不认交接。
- 为了让新 boss 读到老 boss 最后的对话，服务在 boss 新建会话、交出和认领时，把该 boss 原生会话文件的路径（能按 `session_model` 的宿主规则找到时）写进 `workspaces`。这是 ADR-0017 之后数据库里唯一含原生 boss 会话 ID 的地方；原始 `manager_session_id` 本身仍不落盘。

## 取舍

- 不改写会话行的归属，交接就不需要拿到正在运行的会话的锁，也不会和老服务的保存冲突；代价是“谁能写”要多查一张表。
- 老 boss 一旦被认领就不能再用 `start_agent`、`run_round` 在原工作区派活，也不能用同一聊天开新工作区，避免两个聊天同时指挥一组工位；要继续工作就让新 boss 交回来。交接前留下的待审答案由老 boss 在原服务里决定（`decide_answers` 不带 boss 身份）；原服务正常退出时按取消处理、未决回答不公开，崩溃或被强行终止后新 boss 才能决定。
- 待接手不阻止老 boss 继续工作，误点只要老 boss 或用户在原聊天里认领回来即可撤回；被别的聊天认领前工作区不变。
- 托盘交出的工作区如果从未在新版本服务里建过会话，就没有记录到会话文件路径，认领回执只给会话列表。
- 会话文件路径由见到该 boss 的服务按自己的环境（如 `CODEX_HOME`）找到并记录；认领时文件已移走或删除就不给。

## 修订：只有 boss 的工作区与接手 Skill（2026-11-01）

背景：转交只能用于派发过任务的聊天，而接手说明让新 boss 读老会话文件的“尾部”，没有说怎么读。实测尾部 50 行中位约 7.7 万字符、对话文字约占 1%，单行可达数百万字符。曾考虑由服务解析各宿主记录、抽取最近对话放进回执，因要长期维护各家解析器并追加过滤和脱敏而放弃。

决定：

- 用户要求转交时，没有会话的聊天也能交出：`workspaces` 行加 `title`、`cwd`，由这一行承载只有 boss 的工作区，不建占位会话。这样的行等待接手或由新 boss 领导时，不随“最后一个会话被删”清除；用户可在 App 单独删除。撤回后它不再显示，下次清理时移除。两列用 `ALTER TABLE` 加，`user_version` 不变，托盘只读连接遇到旧库时按没有这两列处理。旧程序能打开新库，但不认识这种行：旧托盘删除任意会话、旧服务里这个聊天再认领别的工作区，都会把它删掉。App 会一起升级服务，这个风险只在升级之间存在，不为它加防护。
- 接手的第一步是 `handover()`。只有一个待接手、一天内交出、`cwd` 与当前目录相同且与用户说法不矛盾时才直接认领，否则列出来问；这是 Skill 的约定，服务不强制。
- 老 boss 写不了文档时，用户直接告诉新 boss 接手哪个宿主的会话。这条路只读本机记录，不需要工作区；要用老会话的工位时，仍由用户在 App 里交出，避免两个聊天同时指挥一组工位。
- 转交写法、接手步骤、各宿主会话位置和读取规则放进独立的 `agentnave-handover` Skill，随宿主接入必装：用户只说“接手”时并未要求派发，放在 `agentnave-manager` 里不易触发；额度耗尽是突发的，不能依赖用户提前打开开关。
- 服务只记录老会话在哪、不解析内容。`session_file` 覆盖全部已接入宿主；文件之后被移动或压缩时，回执带 `previous_session_moved`，新 boss 按位置表找。Hermes、ZCode 的会话共用数据库，认领时用工作区键反查会话 ID 并放进回执，会话 ID 仍不落盘。

取舍：读多少靠模型遵守 Skill，服务不设上限；新 boss 读老记录时，其中的密钥会进入它的上下文，读取权限本来就由宿主决定，暴露面没有变大。各宿主格式变化时位置表可能过期，新 boss 读不出来时会告诉用户。
