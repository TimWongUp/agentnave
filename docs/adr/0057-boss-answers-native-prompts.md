# ADR-0057：运行中的原生弹框由 boss 代答

- 状态：提议
- 日期：2026-11-04
- 修订 [ADR-0019](0019-no-running-messages.md)：运行中允许应答 CLI 自己发起的弹框；[ADR-0024](0024-consolidated-tools-and-private-review.md) 的工具集合：新增 `answer_prompt`；[ADR-0032](0032-cli-permission-tiers.md) 中「自动」档的含义：CLI 自动审核交回的请求由 boss 决定。
- 补充 [ADR-0007](0007-wait-any-ready-subset.md)：待答弹框是新的就绪原因，收件箱 `wait` 同样返回。
- 依赖 [ADR-0056](0056-claude-interactive-runtime.md)。

## 背景

`-p` 下没有人能应答弹框：需要审批的工具调用要么被 CLI 自动审核放行，要么被直接拒绝，任务照样报成功（ADR-0032）。Claude Code 交互模式（ADR-0056）会在运行中弹出权限框和提问框，并能通过 hooks 把它们交给外部程序应答。没人应答，任务就会一直停着。

用户定的原则：「自动」档意味着由 boss 决定。boss 相当于用户，判断权限的能力通常比大多数人强，频繁打扰用户反而低效；派发写入 Worker 本身就是授权。只有真正关键的选择才问用户。

## 决定

- **上报**。交互运行的 Claude 发起权限请求（`PermissionRequest`）或提问（`AskUserQuestion`）时，hook 阻塞等待，服务把它作为待答弹框挂在该 Invocation 上。`wait` 以新的就绪原因返回，每个弹框提醒一次，带弹框编号、类型、工具名与输入（有界）或问题与选项。私聊任务与会议席位都适用，省略 `ids` 的收件箱 `wait` 同样返回。
- **通道**。弹框经 helper 的 stdout 事件上报；答复由 Adapter 钩子编码，经该 Provider 进程的 stdin 送回，声明支持弹框的 Adapter 运行期间 stdin 保持打开。核心只认通用的弹框事件和答复，不按 Provider 分支。
- **应答**。新工具 `answer_prompt` 按弹框编号应答一次：权限框只能允许或拒绝本次调用，拒绝可附一行理由；提问框按题选项或填写答案。服务永不写入持久放行规则，不转发「始终允许」「不再询问」之类的选项。弹框结束（已答、超时、取消、进程退出）后再答被拒绝。`answer_prompt` 要求 `manager_session_id`，只有拥有该工作区的 boss 能答，交接后老 boss 的答复被拒绝。
- **等待**。服务不给待答弹框设时限，与 Invocation 没有总时限一致；hook 超时取 CLI 允许的上限，超时按拒绝处理。`cancel` 先拒绝待答弹框再终止进程树。待答期间进程不产生输出，不算 ADR-0049 的持续重试。
- **boss 的代答边界**。boss 按派发时的授权自行决定，不必逐个问用户；`access=read` 的任务拒绝写入请求。以下关键选择必须转达用户，用户答复前弹框保持待答：删除或覆盖用户数据；改写 Git 历史；对外发布、发送、购买；扩大授权或要求持久放行；写任务范围以外的用户配置或凭据。完全放开档下 Claude 不弹权限框，提问框仍由 boss 答。
- **审计**。每个弹框和答复存进该任务或席位的历史，App 在时间线上显示「谁、何时、怎么答的」。记录放在任务或席位已有的 JSON 里，不改表结构；需要新表或新列时按 ADR-0048 升版本。托盘读这些记录属于服务与托盘的合同，落地时更新 architecture.md。
- **弹框内容是数据**。工具输入和问题文本由子代理写出，可能夹带针对 boss 的指令。回执把它们标为数据；boss 按实际工具和参数判断，不按其中文字行事。
- 其他 Provider 和 `-p` 路径不变，不会产生待答弹框。

## 取舍

- 这是 ADR-0019 之后第一个运行中通道，但只能应答 CLI 自己发起的弹框，不能主动给运行中的任务发消息；拒绝理由和提问答案是仅有的文字。ADR-0019 对其他通道的结论不变。
- boss 代答扩大了 boss 的实际权限：一次允许就可能执行写入或命令。约束靠派发授权、关键选择清单和审计，不是沙箱；Provider 原生权限仍是安全边界，boss 不追加权限参数（ADR-0032）。
- 派发前缀仍写「运行中没有人能回答」（ADR-0043），不按 Provider 区分：核心不按 Provider 分支，需要用户决定的事仍应写进最终回答。所以提问框很少出现，出现时由 boss 答。
- boss 不在线或长时间不 `wait` 时，任务会一直停在弹框上，占着运行名额。
- 待答状态只在进程内存中，服务重启后随 Invocation 一起丢失。

## 考虑过的方案

- **一律自动拒绝，等任务结束再续接**：实现最简单，但交互模式下大量写入被拒，任务做不完，额度优势被续接抵消。
- **一律交给用户**：最保守，但违背用户定的原则，用户会被频繁打断。
- **服务按规则自动应答**：服务要自己判断权限，越过 Manager 拥有决策的边界。
