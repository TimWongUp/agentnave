# ADR-0064：派发回执引导收取，可选派发后先等

- 状态：已接受
- 日期：2026-11-07
- 修订 ADR-0007：等待仍由 boss 主动发起，派发调用可以顺带等一次。

结束结果只能由 `wait` 收取（ADR-0007），boss 漏掉 `wait` 就会在任务还在跑时结束回合。真实使用中多个模型出现过这种情况：派发回执只写 `running`，模型把它当成会自动回报的后台任务；`unreceived` 只附在下一次派发回执上，模型不再调用时没有机会出现。同类应用（Paseo、t3code、Cindy、Lody）托管 boss 会话，能在子任务结束后把结果注入 boss 并唤醒它；AgentNave 挂在用户自己的宿主上，没有这条通道，各宿主的推送能力也不一致，所以不依赖推送。

派发回执在仍有待收结果时带 `next`，写明结束回合前先 `wait`；`wait` 返回时若仍有待收句柄，同样带 `next` 要求再次等待。这是模型做决定时一定会读到的位置，比只写在 Skill 中可靠。

`start_agent` 和 `run_round` 提供可选的 `wait`：为真时派发后按 `wait` 的默认时长等待本次句柄，并在回执中返回那次等待的结果，收取语义与单独调用 `wait` 相同。它默认关闭，派发仍立即返回；只用于本回合需要结果的单次派发，并联派发仍应全部派出后统一等待，否则会变成串行。

App 写入宿主全局规则的编排段落加入同样的收取要求（ADR-0037），让每轮都可见；自定义规则不改写。

不做：托管 boss 会话或依赖某个宿主的推送通道；在托盘提示未收取结果。宿主 Stop 钩子能拦住结束回合，但各宿主的信任和入参不同，另行决定。
