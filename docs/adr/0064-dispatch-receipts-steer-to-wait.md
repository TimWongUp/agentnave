# ADR-0064：派发回执引导收取，可选派发后先等

- 状态：已接受
- 日期：2026-11-07
- 修订 ADR-0007：等待仍由 boss 主动发起，派发调用可以顺带等一次。

结束结果只能由 `wait` 收取（ADR-0007），boss 漏掉 `wait` 就会在任务还在跑时结束回合。真实使用中多个模型出现过这种情况：派发回执只写 `running`，模型把它当成会自动回报的后台任务；`unreceived` 只附在下一次派发回执上，模型不再调用时没有机会出现。同类应用（Paseo、t3code、Cindy、Lody）托管 boss 会话，能在子任务结束后把结果注入 boss 并唤醒它；AgentNave 挂在用户自己的宿主上，没有这条通道，各宿主的推送能力也不一致，所以不依赖推送。

派发回执在仍有待收结果时带 `next`，写明结束回合前先 `wait`；`wait` 返回时若仍有待收句柄，同样带 `next` 要求再次等待。这是模型做决定时一定会读到的位置，比只写在 Skill 中可靠。

`start_agent` 和 `run_round` 提供可选的 `wait`：为真时派发后按 `wait` 的默认时长等待本次句柄，并在回执中返回那次等待的结果，收取语义与单独调用 `wait` 相同。它默认关闭，派发仍立即返回；只用于本回合需要结果的单次派发，并联派发仍应全部派出后统一等待，否则会变成串行。

App 写入宿主全局规则的编排段落加入同样的收取要求（ADR-0037），让每轮都可见；自定义规则不改写。

不做：托管 boss 会话或依赖某个宿主的推送通道；在托盘提示未收取结果。宿主 Stop 钩子能拦住结束回合，但各宿主的信任和入参不同，另行决定。

## 修订：收口时补待跟进清单

- 日期：2026-11-18

`unreceived` 只覆盖还没交付的结果；已被某次 `wait` 交付的 `failed`／`blocked` 任务和席位、还没释放的隔离目录，之后没有任何回执再提，多路派发、多次 `wait` 后 boss 容易漏掉。`unreleased_isolation_count` 只在派发回执出现，且按工作区累计存量计数，不适合放进 `wait`。

不收件的 `wait` 收口时（不带 `ids`、`all_finished=true`，含 `nothing_pending`），回执补 `follow_up`，只列早先已交付、当前仍需 boss 处理的项：

- 任务终态为 `failed`／`blocked`，且同工作区没有同一原生 `session_id` 的更新任务（续接即视为已处理）。
- 已结束轮次中仍为 `failed`／`blocked` 的席位，或整轮 `failed`。
- 本进程交付过、未被自动释放、登记仍在且无任务占用的隔离目录。

边界与去重：账本只在服务进程内存，按工作区记录，只记 `wait` 已交付的项；重启即清空，与 Invocation 不跨重启一致。清单按当前状态重算，每项最多出现一次，报过即移出；同一回执的 `updates` 已带的结果不重复列，显式 `ids` 的 `wait` 只记账、不出清单。`cancelled` 是 boss 自己的动作，不列。接手只建关联（[ADR-0099](0099-handover-links-workspaces.md)），账本跟着原工作区走，接手的 boss 不收到。清单最多 20 条，超出给 `follow_up_omitted`。

取舍：换工位或另起线程重派无法确定性关联到原失败项，仍会报一次，所以措辞只说「仍是失败」，不说「未处理」；不为此引入按提示词或角色的猜测匹配。不做后台监控、定时器和自动重跑。
