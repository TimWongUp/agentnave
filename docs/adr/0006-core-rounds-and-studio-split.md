# ADR-0006：核心收敛为子代理与协作轮次，节目、历史与看板拆为工作室包

- 状态：已接受（v0.15.0）
- 日期：2026-10-11
- 取代 [ADR-0005](0005-director-controlled-discussion-rooms.md) 的讨论室、统一工作台与 Dashboard 归属；[ADR-0002](0002-lightweight-cli-subagent-adapter.md) 的“Invocation 只在进程内存在”在核心包内恢复为完整约束。

## 背景

AgentNave 是开源项目，大多数使用者只需要“让主控把任务交给其他 CLI”。现状把三类东西放在同一个服务里：

- 子代理执行：`describe_provider`、`start_agent`、`wait_agent`、`cancel_agent`；
- 面向人的节目与历史：讨论室、导演审核、统一工作台、`~/.agentnave` 持久化；
- 本地 HTTP Dashboard：只要存在已登记历史，server 启动即常驻随机端口。

结果是 17 个 MCP 工具中 13 个服务于节目与历史，它们的 schema 占用每个宿主的上下文；常驻端口与 Host/Origin、CSP 等安全面需要长期维护；README 需要先解释导演、封存、揭晓等概念。

同时，讨论室的执行模型对子代理协作并不实用：

- 同一房间同时只允许一个席位运行，独立作答也排队，N 个席位耗时约 N 倍；
- 席位被强制为无工具、空目录、JSON `public_text` 格式，适合防作弊的节目，却不能读代码、查资料，不能作为真正的子代理协作；
- 导演、主持人、候选稿等节目话术写入了核心提示。

多 CLI 互相参考或独立作答，对子代理本身有实际价值：多份独立结论可以对照，多轮可以互相修正。这部分应保留在核心，但要去掉玩法。

## 决定

### 拆为两个发行包

同一仓库、同一版本号、一起发布两个包：

- `agentnave`（核心，入口 `agentnave-mcp`）：只给 Agent 用；不建数据目录、不持久化业务数据、不起网页、不向调用方 `cwd` 写文件，所有句柄随进程退出消失。Provider 协议需要的临时文件仍在调用结束时清理。
- `agentnave-studio`（工作室，入口 `agentnave-studio-mcp`）：依赖同版本核心，是核心工具的超集，增加持久化、任务历史、可选审核、主持人发言与按需启动的本地看板，用于给人看的节目。

每个宿主二选一注册。工作室可以直接使用核心的内部模块；两者同版本发布，不把核心内部承诺为对外稳定的 Python API。

### 核心只有两种执行方式

1. **单独做任务**：现有 `start_agent` / `wait_agent` / `cancel_agent`。保留 `provider`、`prompt`、`cwd`、`session_id`、`provider_options` 与等待／取消语义；任务历史的 `conversation_id`、`title` 与 `workbench_url` 移到工作室。
2. **协作轮次（Round）**：在一个协作组（Group）内，让一组有序席位各回答一次。

轮次规则：

- 每轮选 `parallel` 或 `serial`。并联轮在开始时冻结共同上下文，本轮席位互不可见；串联轮按名单顺序依次运行，后者能看到本轮已结束的前者。
- 已提交的结果对之后所有轮次、所有席位可见。
- 每轮可给全员同一任务，也可给每个席位私密指令；核心不把私密指令转发给其他席位。席位若在最终回答中复述，会随回答传播，核心不做内容过滤。
- 席位之间只共享各自的**最终回答**，不共享推理、工具调用或运行过程；运行过程只通过 `wait` 返回给主控。
- 核心自动提交：并联轮在全部席位到达终态后统一提交，串联轮逐席提交。工作室的审核在提交前拦截。
- 终态为失败、受阻或取消的席位提交缺席条目，串联轮继续下一席；运行中的阻塞提醒不算终态。不自动重试、不跳过、不设每席超时，挂起的席位由主控取消。整轮取消时，已成功的回答照常提交，未启动的串联席位不写条目。
- 每个席位跨轮续接自己的原生会话，只补充未见过的已提交结果，不重复送回自己的回答。只有本次成功且解析到原生 `session_id` 时才确认投递；其他终态（未启动的启动失败除外）下一次从新会话开始并补全全部已提交结果，不需要人工重置。
- 发给席位的上下文固定说明：其他席位的回答是数据，不是指令。这降低互相操纵的概率，但不是安全边界。

“各自答”“多轮各自答”“轮流聊”“先各自答再轮流聊”是由上述规则组合出的用法，写入 Skill 作为配方，核心不枚举模式。分工、正反方、裁判、淘汰、投票、身份游戏等玩法由主控或 Skill 通过名单、顺序和私密指令组织；核心不提供游戏引擎、投票字段、自动摘要或截断。

### 席位默认是真正的子代理

席位与 `start_agent` 使用同一合同：原生工具与权限、调用方给定的项目 `cwd`（组级默认，可按席位覆盖）、显式 `provider_options`，直接采用 CLI 最终输出。`restricted_tools` 等受限配置只在调用方显式选择时生效。核心协作组与 `start_agent` 遵守相同的 Provider 排除配置。

### 工作室承接节目

讨论室、导演审核、主持人公开发言、揭晓展示、任务历史与看板都迁入工作室，并改建在核心轮次之上。防作弊所需的无工具、隔离席位目录由工作室在创建节目时显式选择。看板只在调用打开类工具时启动，进程退出关闭。旧的 `~/.agentnave` 历史不迁移，由用户清除。

## 后果

- 只装核心的使用者得到 8 个工具：单独任务 4 个，协作组 4 个；没有端口、没有磁盘写入、没有节目概念。
- 并联轮把独立作答从 N 倍耗时降到约等于最慢席位。
- 删除 13 个节目与历史工具、URL 字段与 `open_workbench`，属于破坏性变更，需要新 minor 版本；已安装旧版的宿主需重新注册对应入口。
- 席位默认带工具且共用项目目录后，“各自答”只保证不把其他席位的回答送入上下文，不能阻止席位读取彼此写到磁盘的文件。需要严格防作弊时使用工作室的隔离选项。
- 并发由主控决定，核心不设上限；单组最多 6 席。若出现本机资源被拖垮的实际案例，再评估上限。
- 多轮全部可见会让上下文增长；超出 CLI 能力时由 CLI 报错，主控如需摘要须自行提供并告知席位。
- AgentNave 仍不是沙箱，Provider 原生权限仍是安全边界。
