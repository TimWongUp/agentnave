# ADR-0087：新增「决策模型」档：服务请决策模型在用户自定义的工位里选，派发仍由 boss 发起

- 状态：已接受

- 日期：2026-11-13
- 「决策模型」档下修订：[ADR-0037](0037-app-writes-orchestration-rules.md) 与 [ADR-0068](0068-rules-hold-authorization-skill-holds-method.md) 中「服务不调度」「选工位的方法放 Skill」；[ADR-0038](0038-role-applies-app-seat.md) 与 [ADR-0052](0052-orchestration-specialty-seats.md) 中工位是固定分组乘简单、困难两档；[ADR-0074](0074-app-seat-model-source-and-claude-family-aliases.md) 中工位不可用时「按同难度规则兜底」。扩展 [ADR-0041](0041-orchestration-mode-per-boss.md)：这一档与其他档一样按 boss 选、读同一规则文件的 boss 共用。其他档下上述各篇不变。

## 背景

现在 boss 选工位靠全局规则块里的一段文字：任务类型对应 Explorer、Worker 和几个专项，各分简单、困难两档。工位是产品预设的固定目录，用户只能给每格绑定 CLI 和模型。想加自己的专业工位或更多难度档，就要改规则文字，而这段文字每段聊天都要读，越长越贵。boss 还要自己对照 `list_members` 判断谁在冷却、谁没额度。

2026 年下半年出现了只做选择的决策模型（Gemini Decision 1、Jev）：给定输入和一组带描述的候选项，返回选中项与各项概率，不生成文本，官方给出的中位延迟在几百毫秒内，按输入计费且很便宜。

## 决定

- **单独一档「决策模型」，实验性质。** 它与关闭、只开会、分工协作、并行分工、自定义并列，按 boss 选，读同一规则文件的 boss 共用，生效状态由 App 计算后写给服务，方式与其他档相同。这一档有自己的规则块正文，并自带「并行写入由 boss 判断」和「有分歧时主动开会」两个选项，默认都关。不选这一档就完全是现状。
- **这一档的工位目录是用户自定义的。** 用户在 App 里增删工位，工位从通用工位、专业工位（沿用现有分组及其说明）和自定义工位里添加，自定义工位由用户自己填专业；每个工位按简单、中等、困难分别绑定 CLI、模型和可选 effort，读写类型随工位。固定的 Explorer、Worker、专项分组和单个生图工位在该 boss 下不再公布，生图也进这份目录并可以有多个（按画风等专业区分）；评审工位不受影响。目录存在数据根的独立文件里，不并入现有编排文件。
- **选工位由服务请决策模型做，派发仍由 boss 发起。** boss 调 `start_agent` 时把工位写成自动并说明读写类型，服务把派发内容和当前可派发的工位作为候选发给决策模型，选出后照常启动，回执带上选中的工位、置信度和概率靠前的几个候选。boss 把一件事拆成几项时可以一次交出，服务用一次决策请求为每一项各选一个工位并同时启动。另有一个只读工具只返回推荐不启动，供 boss 先看再定；boss 始终可以直接指定目录里的工位。服务不会在 boss 没有调用时自己启动任务。
- **候选只含真正能派的工位。** 模型池、宿主排除、停用、未安装和冷却沿用现有判断，派发时仍再查一次；与宿主同类的工位照常标为原生工位，由宿主自带子代理执行。
- **调不通就报错。** 没配密钥、网络失败、被限流或地区不支持时返回明确错误，不启动任何任务，boss 从公布的目录里自己选。不回落到旧规则表，不静默重试。
- **服务第一次对外调用模型 API。** 只在该档生效且 boss 要求选工位时发生；发送 boss 写的派发内容（过长时保留开头和结尾）和候选工位的名称、专业说明、难度与读写类型；不另外读取或发送工作目录里的文件。密钥由 App 写入数据根里仅当前用户可读的文件，服务只读。
- **决策模型可换，先只接 Gemini Decision 1。** 服务内部按「输入加候选项，返回选择和概率」定义接口，Provider 专属的请求格式放在各自的实现里。

## 取舍

- **服务开始参与选工位。** 此前选谁完全是 boss 的事，服务只执行。换来的是目录可以由用户扩展、规则块不随工位数量变长、候选先按可用性过滤；代价是多了一条依赖外部服务的路径。每次启动仍是 boss 的一次调用，派发授权、权限和最终责任仍在 boss；决策模型看不到对话，只看得到这一次的派发内容，所以 boss 可以不用它、直接指定工位。
- **做成单独一档，而不是其他档里的开关。** 先做成了「分工协作」「并行分工」下的一个开关，用户看过界面后否决：开关让一个档位有两套工位和两种规则，设置页不干净。单独一档后，工位目录、规则正文和选项各自独立；代价是档位枚举多了一个值，尚未升级的旧版服务读到它会把整个编排文件判为无效，与当初新增「只开会」档时相同。
- **不做成自动回落。** 考虑过决策失败时退回旧规则表，没有采用：两套目录不同，回落等于悄悄换了一组工位；实验期间失败要看得见。
- **一次调用完成选择和启动。** 最初只做了「先要推荐、再派发」两步，每次派发多一个来回；用户要求省掉。合成一步后推荐工具仍保留，因为与宿主同类的原生工位服务启动不了，选中它时只能把结果交还 boss。
- **多项任务一次交出。** 逐项派发时每项都要等一次两三秒的决策请求；决策接口一次请求可以带多个问题（实测三项一次请求约 2.3 秒），所以加了批量入口。拆成几项仍由 boss 决定，批量入口不改变并行写入的授权；一次里有两个及以上可写项时，服务自动给每个可写项建隔离目录，避免 boss 漏传而互相覆盖。
- **不设置信度门槛。** Google 明确说阈值要用自己的流量标定，文档里的 0.7 只是示例。第一版把置信度和候选一并返回，由 boss 判断，积累数据后再定。
- **不让 boss 通过某个 CLI 去问决策模型。** 决策模型不是对话模型，不能当 CLI 的主模型；起一个 CLI 进程来转一次 API 调用，延迟和失败面都比直接调用大。
- **密钥不放系统钥匙串。** 沿用语音密钥的做法：数据根里的文件加文件权限。服务是 Python 进程，要在三个平台上都读得到。
- **发派发内容而不是摘要。** 最初只发 boss 另写的一两句摘要，理由是派发内容不离开本机；用户指出只凭一句话判断不可靠。实测摘要写得含糊时置信度明显下降，而被选中的 CLI 本来就会把同一份内容发给它的模型厂商，所以改为发完整派发内容，boss 也不用另写摘要。
- **派发内容会离开本机。** Gemini 免费层的输入可能被用于改进产品，付费层不会；Google 的可用地区不含中国大陆和香港。这两点在这一档的页面上写明，是否选用由用户决定。
- **Linux 没有 App，也没有设置入口。** 目录和密钥文件可以手写，但实验期间不为无头环境提供单独的说明或兜底。
