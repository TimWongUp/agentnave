# ADR-0085：隔离目录由服务创建、登记和回收，是否隔离仍由 boss 决定

- 状态：已接受
- 日期：2026-11-12
- 修订 [ADR-0002](0002-lightweight-cli-subagent-adapter.md) 中「AgentNave 不提供 worktree」一条；扩展 [ADR-0043](0043-service-prompt-instructions.md) 的服务追加说明。

## 背景

并行写入要求每个写入者有独立的 git worktree。此前建目录、合入和清理全由 boss 在 shell 里完成，服务只在同一 `cwd` 已有运行中任务时给一条事后警告。结果是遗留目录没人清：boss 只看得到自己这段聊天，换一段聊天就不记得建过什么；一个目录能不能删还取决于别的任务是否在用。

对照 T3 Code、Paseo、herdr、Cindy、Claude Code 与 Codex，它们都由服务端或守护进程执行 `git worktree` 并负责回收，也都默认不隔离、由调用方显式申请。

## 决定

- **职责切开**：服务执行 `git worktree` 的创建与删除，登记目录归属，判断能否安全删除。boss 仍决定这次派发要不要隔离、从哪个提交开始、怎么合入、什么时候释放。服务不做合入，不联网，不查 PR 状态。
- **默认不隔离**：隔离是私聊任务的可选参数。不是 git 仓库、没有任何提交或是裸仓库时直接报错，不退回共享目录。会议席位不能申请新建，但可以把已有隔离目录作 `cwd`，运行期间同样占用它，服务不为席位追加隔离说明；宿主自带子代理不经过服务，用宿主自己的隔离。
- **位置**：目录平铺在主工作树根下的 `.agentnave-worktrees/`，并写入仓库的 `info/exclude`。从隔离目录再派发时，起点取它的 `HEAD`，落点仍平铺，不嵌套。
- **起点**：默认取派发目录的 `HEAD`，boss 可指定；先解析成提交，再建一个新的受管分支，从不检出已有分支。解析不了就报错。派发目录里未提交的改动不带过去，回执里说明。
- **环境**：只按仓库根的 `.worktreeinclude` 复制被 git 忽略的文件，有数量和体积上限。服务不执行 setup 脚本。建目录时跳过 git hooks 和 LFS 下载并在回执里告警；有子模块或其他自定义 filter 的仓库拒绝隔离。
- **登记**：存在数据根的独立文件里，不进会话库，也不随工作区历史被清理而消失。同一仓库的创建、认领和删除用仓库级锁串行；运行中的任务对所在隔离目录持有跨进程可见的使用租约，锁和租约文件放在仓库的 git 公共目录里，由服务进程持有。
- **只显式释放**：boss 释放后服务才删目录和受管分支。释放即表示接受丢弃目录里被 git 忽略的文件；有未提交的源码或未合入的提交时，释放要带绑定当前提交的确认。服务自己只回滚本次创建失败的半成品，并续删已开始删除的残局。任务失败或取消时目录原样保留。
- **别的聊天也能释放**：隔离目录登记在创建它的工作区名下，回执提醒只算本工作区的。任何 boss 都可以按仓库列出并释放其他工作区的隔离目录，这时无论目录是否干净都要先确认，且不能有任务在用。
- **服务追加的说明**：隔离任务的前缀增加事实和边界——隔离目录与分支、主目录在哪、不改主目录、不推送、不切换分支，以及任务要求修改主目录下的文件时改动隔离目录里的对应路径。是否提交由 Skill 和 boss 的简报决定。追加项在回执 `defaults_applied` 注明。
- **回执与历史**：终态回执带隔离目录的改动摘要；任务历史记录目录和分支；派发回执提醒本工作区还有几个未释放的隔离目录。

## 取舍

- **服务开始在用户仓库里建目录和分支。** 此前服务从不碰用户仓库。换来的是归属可查、删除有统一的检查；代价是删错的责任在服务，所以第一版不做任何未经 boss 释放的删除。
- **不自动回收未释放的目录。** 考虑过扫描后自动删「干净且提交已合入」的目录，没有采用：被 git 忽略的文件不出现在 `git status` 里，删目录时会一起丢；压缩合并和变基合并后，本地 git 也看不出分支是否已合入。遗留靠回执提醒和 App 显示暴露，是否补过期策略看实际使用再定。
- **放仓库内而不是数据根。** 集中目录不污染仓库、天然不嵌套，但会破坏依赖相对路径的工具链。仓库内目录可能被项目自己的工具扫到，服务只写 `info/exclude`，不改项目配置。
- **不执行 setup 脚本。** 依赖由子代理自己安装；每个隔离目录都要重装，大项目会慢。目录复用暂不做。
- **提交约定不由服务追加。** 同一个隔离目录还会派给只读复核者，也有只改不提交的任务；服务只知道事实，不知道任务要求。
- **不按工作区限制释放。** 考虑过只让创建它的工作区释放，没有采用：最常见的遗留正是 boss 建了目录后那段聊天被关掉，之后的聊天无权清理，App 也不提供清理入口。同一用户本机内的各段聊天之间本来不设防，会话 ID 也不是认证手段。
- **不用隔离的用户不受影响。** 不建 git 仓库或习惯直接在主分支改的用户照旧在共享目录里逐个派发写入任务；服务不替用户 `git init`。
