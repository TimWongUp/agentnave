# ADR-0020：首次预填各 CLI 的主力模型

- 状态：已接受
- 日期：2026-10-20

部分修改 [ADR-0013](0013-members-defaults-and-host-identity.md) 中「无配置文件时保持原生行为」。

## 背景

没有 `members.json` 时，调用方省略 model 就沿用 CLI 原生模型，工位身份里的请求模型为空。Grok、Antigravity、DeepSeek 的输出不一定能确认实际模型，办公室里因此会出现大量「默认模型」工位。

## 决定

App 在数据根既没有 `members.json`、也没有待迁移的 `profiles.json` 时，探测一次本机 CLI，写出首份组员配置：

- 两种模式都列出全部 Provider，模型列表为空，即不限模型，放行范围与缺失文件时相同。
- 探测能确定主力模型的 CLI，在两种模式下都设为默认模型，并加入共享模型：
  - Codex 取模型缓存中优先级最高的 `gpt-` 模型；
  - Claude 取 `opus`；
  - Antigravity 取 `agy models` 的第一项，即 agy 自己的默认模型；
  - Grok 取列表中标为 default 的模型；
  - DeepSeek 取内置目录中标为 default 的模型。
- Pi 与 CodeBuddy 的列表不标默认模型，不预填，继续用原生模型，实际模型由各自的原生回报确认。
- 没有任何 CLI 能确定主力模型时不写文件。

只预填缺失的文件：写出后由用户在设置页修改，App 不再补填，也不覆盖。设置页开启「自选可用工具和模型」或启用某个 CLI 时，同样把探测到的主力模型设为该模式的默认模型。

预填发生在 App 启动时的后台线程，以及 `GET /settings/members` 读取缺失文件时，与旧档案迁移共用同一把互斥锁。

## 取舍

- 选在 App 里预填，而不是让服务或 Adapter 在调用时自动选模型：Adapter 不静默设置模型的边界不变，默认值仍是用户可见、可改、在回执 `defaults_applied` 注明的组员配置。
- 默认模型覆盖了 CLI 自己的模型配置。要用原生模型，在设置页清除该 CLI 的默认模型即可。
- 首份配置使两种模式变为受限：以后版本新增的 Provider 不在名单里，需要用户在设置页启用。
- 服务侧和 `members.json` 的格式都不变，但预填会列出全部 Provider，包括 v0.30.0 新增的 DeepSeek。v0.30.0 之前的服务不认识 `deepseek`，会以 Invalid members.json 拒绝预填后的文件，每次调用都报错。宿主仍连着旧服务时，等中继在空闲时换用已安装的新版本即可恢复；按 2026-07-28 协议连接的宿主（如 Claude Code）若仍由不支持该协议的旧中继转发，中继不会换新，需重启一次宿主。

## 修订（2026-10-21）

- 主力模型先取 CLI 自身设置指定、且在探测列表中的模型（Codex `config.toml` 的 `model`、Claude `settings.json` 的 `model` 去掉 `[1m]` 类后缀、Pi 的 `defaultModel`、Antigravity CLI 的 `model` 标签），再按上文规则；仍无法确定时取列表第一项。Pi 与 CodeBuddy 因此也会预填默认模型。
- 预填的默认模型同时写入默认思考档位：该模型思考档位（按低到高排列）的中间档，偶数个时取偏低的一档。设置页新开始配置某个模型时同样预选中间档；已有配置中未设默认档位的模型不补填，仍交给 CLI 自行决定，直到用户在设置页选定。
