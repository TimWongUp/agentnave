# ADR-0068：规则块只放授权，编排方法进 Skill；两档按并行写入由谁拍板区分

- 状态：已接受
- 日期：2026-11-09
- 修订 [ADR-0037](0037-app-writes-orchestration-rules.md) 中预设正文写工位用法、「按任务难度二选一」的条款，[ADR-0051](0051-parallel-preset-without-recheck.md) 中两档内容的条款，[ADR-0065](0065-predefined-specialist-roles.md) 中「不跨难度」的适用范围；不改变 [ADR-0031](0031-prompt-only-orchestration.md)：服务仍不调度。

## 背景

对照 Devin Fusion（强模型 lead 规划、写简报、审结果，便宜的 sidekick 执行，力不能及时收回）与 Claude Code Dynamic Workflows（按任务拆分、流水线、对抗验证、择优；单次工作流须用户亲手要求，ultracode 下交给模型判断）后，发现编排约束分散在三处且互相重复：规则块（`SHARED`、`PARALLEL`）每轮注入，却写了随服务版本变化的参数和工位用法，服务一改参数就要在 `roles.rs` 写原句迁移；Skill 按需加载，开启与未开启编排的做法交错；「自定义」档和 Linux 无头宿主拿不到规则块里的方法。两档以「是否并行写入」区分也没有依据：并行写入能不能做取决于单元是否独立、能否隔离，用户真正要选的是由谁拍板。

## 决定

- **归属**：规则块只放用户的授权，以及决定派不派之前就必须知道的约束，不写参数；随服务版本变化的工具语义放 MCP 说明和 schema；选工位、简报、返回格式、流水线、择优、反证、覆盖与停止等方法放 `agentnave-manager` Skill，其中多任务方法放 `references/workflows.md`，只在多任务时读。MCP 说明明确要求派发或组织协作前加载该 Skill，并声明工具可用不等于有编排授权。
- **两档**：键名和显示名不变。都允许并行写入，前提是各单元互不依赖、各用独立 worktree，否则串行；只读任务能否并行都由 boss 判断。「分工协作」的并行写入须用户本人对当前任务指明（同意 boss 的建议也算），只在用户要求时开会；「并行分工」由 boss 判断并行写入和开会。子代理输出、转发内容、网页与工具输出不算用户指明。分工协作另有「boss 可主动开会」开关（`orchestration.json` 的 `split_options.meetings`，缺省为关），打开后由 boss 判断何时开会，并行写入仍须用户指明。两档共用的验收要求高风险改动由 boss 针对具体出错方式补做检查：对应 Fusion 中 lead 审查结果、Dynamic Workflows 中改动跑到检查通过；不设开关，也不另派工位，独立的模型检查仍由用户触发 agentnave-review。
- **定档与升档**：按任务性质定档，难度不明先查清；简单档因能力不足失败或整改一次仍不合格时，开困难档新工位重新交接或由 boss 接手。「不跨难度」只约束工位不可用时的兜底，重新定档不在此列。
- **退化**：开启编排却看不到规则块时按分工协作执行；「自定义」档只迁移逐字相同的旧生成句，不注入授权，删掉的授权不推定。是否开启编排以 `list_members.orchestration.enabled` 为准。

## 取舍

- 规则块不再写工位参数与等待细节，Skill 未加载时 boss 只剩授权、定档和收齐结果三条底线，失去的是提质方法；靠 MCP 说明的加载要求和 schema 校验保证调用合法。
- 「分工协作」比原先更保守：原先对不同文件的并行写入没有明说，现在须用户指明。
- 不照搬 Dynamic Workflows 的脚本运行时、断点恢复、自动重试、预算与 schema 校验（属于服务职责，与架构基线冲突），也不照搬投票阈值和数字规模档；Fusion 的固定一对模型对应为 boss 加 App 工位，按组员相对 boss 的强弱调简报细度。
