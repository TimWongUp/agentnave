# ADR-0099：接手改为建立关联，工作区不再转移

- 状态：已接受
- 日期：2026-11-16
- 取代 [ADR-0033](0033-boss-workspace-handover.md) 中归属转移的部分：认领后工作区整体归新 boss、新 boss 新建的会话存进原工作区、老 boss 写入被拒、认领要求新 boss 名下没有其他有会话的工作区，以及 2026-11-15 修订（被接手的聊天新建工作区、显式续接维持现状）。转交、撤回、交接说明、App 交出与取消交接、老会话文件位置等其余条款不变。
- 修订 [ADR-0017](0017-manager-chat-session-identity.md) 允许的跨 boss 显式续接；修订 [ADR-0046](0046-service-history-retention.md) 的清理计时起点；新表按 [ADR-0048](0048-sqlite-schema-evolution.md) 提升 `user_version`。

## 背景

ADR-0033 把接手做成归属转移，带来几个问题：已经派发过的聊天认领时会被拒（一个聊天只能带一个工作区），只能另开新聊天，或先把自己的工作区交出去；老 boss 被认领后写入被拒；同一个办公室前后挂着两个 boss。为此陆续加了 `origin`、`former_bosses` 和「被接手的聊天另开工作区」等补丁。

新 boss 接手时真正需要的只有三样：读交接说明和历史，把旧结果带进新任务，接着把活干完。读取本来就不要求归属（`list`、`read_conversation` 对任何工作区都可读），只有 `forward` 限于本工作区。续用旧员工也不划算：接手多发生在中断之后，旧线程的缓存早已过期，续接要整段重建。

## 决定

- **转交照旧，接手只建关联。** 老 boss 或用户（App）照旧写交接说明、标「待接手」，可以撤回或取消。任何 boss 聊天都能在用户要求时认领，包括已经有自己工作区的聊天。认领在一个事务里写一条关联（来源工作区、认领者的 Manager Session 键、接手时间、新宿主），并清掉待接手标记；不改 `owner`，不删认领者的工作区行。重复认领同一来源是幂等的，并发认领只有一个成功；认领自己的待接手工作区仍然算撤回。回执内容不变：交接说明、会话列表、老会话文件位置、隔离目录。
- **各干各的。** 新 boss 的派发、会议和隔离目录都记在自己的工作区里，每个办公室只有一个 boss。老 boss 不再被拒写，照常使用自己的员工。老工作区被接手后，老 boss 下一次派发时回执带一条 warning，提醒先核对工作树，之后不再提醒。是否提醒由关联时间和上次派发时间判断，不另记状态。
- **关联只开放 forward，有方向、不传递。** 目标工作区可以 `forward` 直接来源工作区里已成功的任务和已提交的条目，注入时注明来源工作区；不能 forward 来源的来源。被打断或失败的半成品不放开 forward，由新 boss 读出来写进简报。
- **员工按工作区独占。** `start_agent` 用 `session_id` 续接时，私聊任务和会议席位绑定的原生线程都算已知线程；属于其他工作区的一律拒绝，显式传了 `provider` 和 `cwd` 也拒绝，并提示新开员工、用 forward 带上旧结果。拿到原生会话锁之后再检查一次。旧会议室仍只能由所属工作区续开。保证范围限于同一数据根里现存的记录：历史清理后不追溯，不建永久的线程归属表。本工作区会议席位的线程能否拿去私聊续接，这次不改。
- **运行控制不跨工作区。** 交接时还在跑的任务和轮次留在老服务里跑完，`wait`、`cancel`、`answer_prompt`、`decide_answers` 仍由老 boss 负责；新 boss 只读已经落库的结果。老 boss 无法操作时，由用户关闭老宿主，服务退出时会清理进程树。App 不增加取消运行中任务的入口。
- **隔离目录归属不变。** 租约和清理责任仍属于原工作区。新 boss 可以读旧目录；要接着改时，已提交的进展用 `isolation` 的 `ref` 从提交新建目录，未提交的改动等旧写入停下后，由新员工用 `git diff` 带进新目录；旧目录还在使用中时不进去。这些写进 `agentnave-handover` Skill，服务不自动复制工作树里未提交的内容。
- **接手算一次活动。** 工作区的清理计时起点取「最后一次会话活动、交出时间、最近一次被接手时间」中最晚的那个。被接手后已经没有会话、只有 boss 的工作区，也按这条规则随保留天数清理；待接手且没有会话的，仍然满 90 天过期。Python 服务的清理、托盘的清理和预计删除数用同一套语义。关联不阻止删除，一端被清理后，另一端显示「已清理」。
- **App 显示关联。** 认领时不建占位工作区。新 boss 第一次派发之前，来源办公室显示纯文字「已由 <宿主> 接手」；第一次派发之后，两边互为链接（「接手自…」「已由…接手」）。
- **旧数据原样保留。** 升级前已经按 ADR-0033 转移过的工作区保持原状，包括 `owner`、`origin`、`former_bosses`，以及托盘里「同一工作区换 boss」的显示；新的认领不再写入这些结构。等这类工作区按保留天数清完，再另行删除旧代码。

## 取舍

- **只删「一个聊天一个工作区」的限制也能让已派发的聊天接手**，但会保留跨工作区续接、同一办公室换 boss 等全部包袱。改成关联后，每个办公室只有一个 boss，服务和托盘反而更简单。
- **禁止跨工作区续接员工是兼容行为变化。** ADR-0017、ADR-0033 原本允许显式身份跨 boss 续接。改了之后，旧线程里没写进回复的推理细节带不过来；换来的是员工只出现在一个办公室，两个 boss 不会先后指挥同一条线程。中断之后缓存多半已过期，续接本来也要整段重建。
- **只保证现存记录之间不跨工作区续接。** 永久的归属表要维护一份不随历史清理的数据，和按天清理的初衷相违；历史清理后那个工作区已经不存在，也就不会有同一员工挂在两个办公室的情况。
- **接手顺延保留期。** 旧工作区会多保留一整个保留期，换来新 boss 不会读到一半材料就被清掉。保留期不沿关联链传递，也不会无限续期。
- **老 boss 只提醒一次。** 讨论中有人认为两边并行干活是正常的，每次都提醒会让正常派发看起来像出了错；最后折中为接手后第一次派发时提醒一次。
- **不做跨工作区代答、代取消，也不在 App 里加取消入口。** 这样 App 不需要控制服务进程，不打破 architecture 里的所有权划分；代价是老 boss 失联时，运行中的弹框只能等用户关闭老宿主。
- **旧数据不迁移。** 要拆开新老两任 boss 混在同一工作区里的会话，就得改写会话归属，难以撤回；代价是旧代码要多留一段时间。
