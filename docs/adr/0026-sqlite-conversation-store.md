# ADR-0026：会话存储改为 SQLite

- 状态：已接受
- 日期：2026-10-24
- 修订 [ADR-0008](0008-tray-app-reads-studio-snapshots.md) 的视图快照位置、[ADR-0012](0012-tray-conversation-cleanup.md) 的删除对象与锁位置；会话语义、写入归属、live 运行文件与 Provider 原生会话的归属不变。

## 背景

每个会话曾是一个目录：`state.json` 是权威状态，`views.json` 是托盘投影，`.lock` 是写入归属。每次保存都整份重写这两个文件并 fsync，长会话一生的写入量随长度平方增长（实测 37 轮的节目单个 `state.json` 356 KB、`views.json` 459 KB，每轮保存多次）。跨会话的问题——某个原生 session、轮次或消息属于哪个会话——只能把全部会话读进内存逐个查。接下来要做的收件箱式等待、幂等键、活动摘要、增量读取与待处理请求，都是跨会话索引、只追加或需要事务的数据，继续用文件就要自己实现一个没有事务的弱数据库。

当前处于快速迭代期，已有会话没有需要保留的内容。

## 决定

- 数据根下的 `agentnave.db`（SQLite，WAL，`synchronous=FULL`，`busy_timeout` 5 秒，外键开启）是会话的唯一权威存储。表：`conversations`（会话头、席位与原生会话绑定，`rev` 每次写入加一）、`entries`（只追加，`position` 即消息序号）、`rounds`、`tasks`（含 `provider`、`session_id`、`status` 索引列），以及派生的 `views`（托盘投影，独立的 `rev` 与写入时间）。条目、轮次与任务的正文以 JSON 存放，索引列只复制需要查询的字段。
- 保存只写与上次保存相比变化的部分：会话头有变才更新，新条目追加，变化的轮次与任务逐行更新，视图内容不同才重写；全部在一个 `BEGIN IMMEDIATE` 事务内。读者按 `rev` 判断是否需要重读。
- 写入归属仍是每个会话一把 OS 锁，锁文件移到 `locks/<会话ID>.lock`，从不删除；“被其他服务占用”“崩溃残留显示为中断”等语义不变。原生会话启动锁仍在 `native-session-locks/`。
- 隔离节目的席位目录移到 `seats/<会话ID>/<席位ID>`。
- 托盘以只读连接读取 `views`，按 `rev` 复用解析缓存；删除与改名在同一把会话锁内对数据库执行，删除级联清除该会话的条目、轮次、任务与视图，保留锁文件与席位目录。
- 不导入、不读取旧的 `conversations/<id>/state.json` 与更早的历史格式，相关兼容代码一并移除。数据库版本记在 `user_version`；版本不符时报错，由以后的迁移代码处理。

## 取舍

- 单文件损坏影响全部历史，不再局限于一个目录；以后需要 schema 迁移时先用 `VACUUM INTO` 备份，平时不做周期备份以免持续写盘。
- 运行中的回复尾巴仍写 live 文件，不进数据库：它每 1.5 秒变化一次，进库就成了持续写盘。
- 视图仍是每个会话一整份 JSON，内容变化时整份重写，写放大比权威状态小但仍存在；托盘直接从表投影后可去掉，暂不做，以免投影逻辑在 Python 与 Rust 各写一份。
- 进程仍把读到的会话状态缓存在内存中，`list` 仍逐个比较 `rev`；按需查询的索引留给后续功能使用。
- 托盘需要打包 SQLite（rusqlite bundled），应用体积略增。
- 不能再直接打开 JSON 查看会话；用 `read_conversation` 或 SQLite 客户端读取。
