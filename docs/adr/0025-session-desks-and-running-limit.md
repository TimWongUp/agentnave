# ADR-0025：工位即原生线程，并发上限决定显示上限

- 状态：已接受
- 日期：2026-10-24
- 取代 [ADR-0023](0023-explicit-desk-continuation.md) 的 `continue_desk`，修订 [ADR-0018](0018-office-workspace-desks-and-meeting-rooms.md) 的工位身份；会议室、转发与 Manager 拥有编排决策的约定不变。

## 背景

工位曾按 `(provider, model, role)` 合并。两个目的不同的任务只要 CLI、模型和角色相同，就落在同一个工位上，App 只画一个人；要分开显示，只能靠 boss 给每个目的起不同的 `role`。这等于把显示正确性交给提示词约束，很脆弱。宿主自己的子代理也不是这么组织的：每次派发默认是一个新的子代理，续接时找的是同一个子代理，而不是同一类角色。

`continue_desk` 依赖这套合并身份去找“同工位最近的线程”。工位不再按角色合并后，它就退化成显式 `session_id`。

服务端也不限制同时运行的 CLI 数量，每个任务都是完整的进程树；工位一旦按线程计，长聊天中的工位数会随派发次数增长，App 每次轮询都要返回并绘制全部工位。

## 决定

- 一个工位就是一条 Provider 原生线程：私聊任务及其用 `session_id` 的续接是同一工位，会议节目的每个席位各是一个工位。`role`、模型与访问等级只是显示标签，取最近一次。
- 移除 `continue_desk` 与回执中的 `resumed`。续接只用 `session_id`；上下文里找不到时，从 `read_conversation` 读回。
- 新增同时运行上限：用户在 App 中设置 1–32，默认 8，存于数据根 `settings.json`。每个服务在接纳私聊任务或轮次前检查：私聊计 1，并联轮计席位数，串联轮计 1；还有席位要启动的串联轮在换席或等待审核、没有席位运行时仍占 1 个名额；超出即拒绝，不排队。
- App 办公室最多画出同样数量的工位：运行中与待审的总是画出，其余按最近活动填满，剩下的进入「已优化」组，只以文字列出。截断在托盘路由中完成，单次轮询的数据量有上限。

## 取舍

- 移除参数又是一次破坏性变更；与尚未发布的工具收敛一起发布，用户只需更新、重连一次。当时服务忽略未知参数，旧调用方传 `continue_desk=true` 会静默得到新线程，由同版本 Skill 更新说明；v0.45.0 起未列出的参数一律拒绝，`continue_desk` 也随之报错。
- 上限按服务进程计算，多个宿主连接各自计数，整机总数可达各自上限之和；跨进程计数需要读写共享运行文件并处理竞态，暂不做。
- 串联轮到最后一席启动前一直占 1 个名额：等待审核可能持续很久，若只在换席时补算，每个待审的串联组都会让总数多出一个。这一预留只计入接纳检查，不排队；轮内后续席位启动时不再检查。
- 超出即拒绝而不排队，与 Claude Code 的子代理上限一致；排队等于由 AgentNave 调度，仍由 Manager 决定何时重派。
- 显示上限与并发上限共用一个数，避免两个相互影响的设置；运行中与待审的工位不受显示上限截断，跨多个服务时画出的数量可能超过设置。
- 尚未拿到原生 session 的运行中任务先按任务记录占一个工位，结束拿到 session 后改按线程归并。
