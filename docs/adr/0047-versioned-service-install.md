# ADR-0047：App 按版本安装服务并在启动时跟进

- 状态：已接受
- 日期：2026-11-03
- 修订 [ADR-0010](0010-launcher-relay-swaps-upgraded-server.md)：App 安装的新版本在宿主重连后生效，空闲热切换只适用于原地重装。
- 修订 [ADR-0014](0014-tray-members-and-one-click-update.md)：更新服务不再需要用户点击，App 每次启动都跟进配套版本。

服务是宿主启动的独立产物，App 每次启动时都把它对齐到配套版本，不等用户点击更新。每个版本单独装进 App 数据目录下的 `service/<版本>/`，装完后由 `service/active.json` 指向它，宿主下次启动服务时改用新版本。正在运行的服务一直使用自己的目录：Windows 不允许删除正在运行的文件，POSIX 则会在进程运行中把文件删掉，所以不能原地覆盖。

中继启动后对自己所在的版本目录持有共享锁 `service/.leases/<版本>.lock`，子进程会继承这把锁。App 只回收满足全部条件的旧版本：带 `gc-v1` 标记、不是当前版本也不是回滚目标、超过七天宽限期、能拿到排他锁。条件都满足后先原子改名，再删除。没有标记的旧版本或手动安装的服务一律不回收。

## 生效时机

中继的空闲热切换只看自己所在环境的安装是否变化（ADR-0010），因此只适用于原地重装，例如 Linux 上执行 `uv tool install --force`。App 按版本安装后，宿主要重连或新开会话才会用上新版本；托盘发现连接的版本落后时，立即提示「需要重连」，不再等待热切换。

## 考虑过的方案

- **让中继读取 `active.json`，跨版本热切换**：能兑现「不断线升级」，但中继要换用另一个环境的 Python 启动子进程，还要在新旧两个版本之间交接运行租约，跨进程改动大，必须实测验收。重连的代价只是宿主上一次重新连接，因此不采用。
- **更新服务仍需用户点击**：用户不点，旧服务就一直留着，新 App 与旧服务的兼容层也得长期保留（见 [ADR-0050](0050-v1-compatibility-baseline.md)）。
