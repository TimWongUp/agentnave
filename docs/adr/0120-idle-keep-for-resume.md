# ADR-0120：Provider 进程答完后保留一段时间，供续接复用

- 状态：已接受
- 日期：2026-11-24
- 修订：[docs/context/architecture.md](../context/architecture.md)「每次 Invocation 由专用 supervisor 持有进程组，正常结束也先清理整组」：支持保留的 Provider，回合正常结束后进程组留在保留期内，到期、被挤出或服务退出时再清理。
- 补充：[ADR-0095](0095-provider-terminal-grace.md) 的终态宽限只适用于不保留的运行；[ADR-0025](0025-session-desks-and-running-limit.md) 的同时运行上限不计保留中的进程；[ADR-0010](0010-launcher-relay-swaps-upgraded-server.md) 的 `restart_safe` 不因保留中的进程拒绝换进程。

## 背景

每次派发都新起一个 CLI 进程，答完即退。实测 Codex 每次调用固定要付约 5 秒：进程启动并载入会话约 1.6 秒，每个新进程每轮开始前初始化约 3 秒（与 MCP、apps、plugins、用户配置无关），模型回一个词只要约 1.4 秒。同一个 `codex app-server` 进程里的后续回合只要 1.3–1.4 秒；`exec` 续接约 6.6 秒。其他 CLI 估计的冷启动从约 0.6 秒（Claude）到约 9 秒（Antigravity）不等。

boss 拿到结果后常在几十秒到一两分钟内续接（追问、复核、整改），每次续接都重付冷启动。用户不接受进程常驻，要求可回收。

## 决定

- **保留期**。支持保留的 Provider，回合正常结束后进程不退出，留 3 分钟。期间同一原生会话续接，新回合直接发进这个进程，计时清零；到期没有续接，服务按现有进程树清理路径结束它。3 分钟先固定，不做设置项。
- **一会话一进程**。保留中的进程只服务它所在的原生会话。新线程、别的会话照常新起进程。
- **能复用的条件**。按启动签名复用：可执行文件、命令行参数、工作目录、账号、额外环境变量，以及 Adapter 申报的启动依赖（Codex 为会影响权限的各层配置文件的大小与修改时间）都相同才复用；任何一项不同，先结束保留中的进程再冷启动。能按回合传的设置（模型、推理档）由 Adapter 在回合里传，不计入签名。
- **不保留的情形**。取消、失败、受阻、超限终止、终端模式派发、在隔离目录里运行，以及 Adapter 没有声明保留能力时，一律照旧结束进程。隔离目录会在任务结束后自动释放或被显式释放，保留的进程会继续占着已删除的目录。
- **数量上限**。保留中的进程最多 3 个，超出时先结束最久没用的。保留中的进程不计入同时运行上限；它被复用时重新按一次运行接纳。实测一个空闲的 Codex `app-server` 连同它拉起的用户 MCP 服务约 550 MB。
- **生命周期边界**。保留中的进程仍归原 supervisor 的进程组（Windows 为 Job Object）所有，服务退出时与运行中的进程一样尽力清理；不跨重启恢复。`restart_safe` 不把保留中的进程算作换进程会丢的状态：丢了只是下次冷启动。
- **归属**。保留期、签名比对、上限与回收在核心（`InvocationManager`）实现，不按 Provider 名分支；Adapter 只声明是否支持保留，并提供「建立长连接」「在已有进程里发下一回合」「判定回合结束」的钩子，协议细节留在 Adapter。
- **权限与新起的一次性进程一致**。长连接协议允许续接时恢复会话里保存的权限，进程内也会沿用上一回合的设置。Adapter 的启动覆盖和发给长连接的请求，与 CLI 一次性命令发给同一协议的逐字段一致（Codex 照 `codex exec` 发给内嵌 app-server 的），由 CLI 按同样的配置层解析权限，使每回合的权限与新起一次性进程时一致，不沿用会话或进程里残留的值；一次性命令不传的权限字段，Adapter 也不传。
- **只在权限完全确定时走长连接**。只有派发的权限参数本身就定死了审批策略、审核者与沙箱（Codex 的「自动」档 `approve_for_me` 与「完全放开」档 `dangerously_bypass_approvals_and_sandbox`），才走长连接并保留。其余情况（未给权限参数、只给 `sandbox`、受限工具、讨论模式）权限要由 CLI 结合用户配置、受管 requirements、目录信任和平台沙箱能力解析，照旧走一次性进程、不保留。Adapter 不复刻 CLI 的权限解析。
- **首批接入 Codex**。Codex 满足上一条的首次派发改走 `codex app-server`：建线程，按回合发 `turn/start`，以 `turn/completed` 结束一轮；之后的续接由保留中的这个进程服务。没有可用的保留进程时，续接照旧走 `exec resume`：app-server 的 `thread/resume` 只有带上客户端自己解析出的权限才不恢复会话里保存的值，这份解析只有一次性的 `exec` 自己做得到。其他 CLI 按实测收益逐个接入，各自真实调用验收后再改。

## 取舍

- 保留期内每个进程占内存（Codex 约 550 MB），换来 3 分钟内续接省下约 4.5 秒；上限 3 个把最坏占用控制在约 1.6 GB。
- Codex 从 `exec` 换到 `app-server`，依赖它标注为实验性的协议；协议握手或方法失败时报错，不静默退回 `exec`。保留期外的续接仍走 `exec resume`，不提速。
- 权限要靠 CLI 解析的派发不提速。App 的两个权限档都给出确定值，常规派发都能提速；复刻 CLI 的权限解析会随 CLI 版本、受管配置和平台不断出偏差，可能把只读放宽成可写，不值得。
- 签名不同就冷启动，放弃了「同一进程里改启动参数」的复用，换来实现简单、权限含义不变。
- 进程在回合之间存活，Provider 若在空闲时自行写盘或联网，发生在 Invocation 之外；结果仍以回合内事件为准。

## 考虑过的方案

- **常驻**：一直保留直到服务退出，无法回收资源，用户否决。
- **只减少每轮初始化**：逐个关掉 Codex 的 MCP、apps、plugins、用户配置后初始化最多省约 0.5 秒，不解决问题。
