# ADR-0010：入口经中继启动，升级后在空闲时自动换用新服务

> 双入口和核心内存组固定旧进程条款已被 [ADR-0016](0016-single-core-and-mcp-entrypoint.md) 取代；中继的空闲升级机制继续沿用。

- 状态：已接受
- 日期：2026-10-15
- 修订 [ADR-0008](0008-tray-app-reads-studio-snapshots.md) 第 6 条：托盘可一键升级本机服务。

## 背景

宿主为每个连接启动一个 MCP 进程，并在宿主进程存活期间一直使用它。`uv tool install --force` 替换安装后，已运行的进程仍用内存里的旧代码；旧工具目录被删除后，尚未加载的模块还可能导入失败。宿主不会因磁盘上换了版本而重连：Claude 只能在会话里手动重连，ChatGPT 应用中的 Codex 等常驻进程要退出整个应用。用户不希望每次升级后逐个处理宿主。

## 决定

1. `agentnave-mcp` 与 `agentnave-studio-mcp` 改为启动一个只用标准库的中继（`agentnave.relay`）。中继把真正的服务作为子进程运行（`python -P -c "from <模块> import main; main()"`），逐行转发 STDIO 上的 JSON-RPC，子进程 stderr 直通宿主。
2. 中继每 5 秒查看所在 site-packages 中 `agentnave-*.dist-info` 的名称与 `RECORD` 修改时间。指纹变化并在下一次检查时保持不变后，才尝试切换；安装过程中目录缺失时不动作。
3. 只在空闲时切换，空闲指：
   - 两个方向都没有在途请求；
   - 子进程报告没有运行中的 Invocation，且每个已结束 Invocation 的结果都已由等待或取消返回过（`list_invocations` 新增的 `result_read`）；
   - 核心入口在本连接中从未调用过 `open_group`。核心协作组只在内存里，所以一旦开过协作组，就固定使用旧进程，直到宿主重连。

   工作室的节目从保存的历史重建，不受此限制。

4. 切换时暂存宿主新来的消息，启动新子进程，并重放宿主原来的 `initialize` 请求和 `notifications/initialized`。新子进程握手成功后，再关闭旧子进程的输入并等它退出；最后把暂存的消息交给新子进程。新子进程启动失败时保留旧进程，等下一次安装变化再试。宿主始终不断线。
5. 宿主关闭连接时，中继关闭子进程的输入并以其退出码退出。子进程自行退出时，中继随之退出，与没有中继时行为一致。
6. 托盘的“本机服务较旧”提示提供“一键升级”：托盘找到 uv，执行与文档相同的卸载旧工作室工具和安装命令，并显示进度与结果。失败时可重试或复制命令。托盘仍不调用 MCP 工具、不写数据根。

## 后果

- 每个宿主连接多一个只用标准库的中继进程。中继自身的代码要到宿主重连才更新，因此保持极小、只依赖标准库，启动时即加载完全部代码。
- 升级后宿主看到的工具列表不会刷新。新版本新增的工具要在宿主重连后才出现，已有工具立即使用新代码。
- 工作室切换后，按需看板的地址会更换，与服务重启相同。
- 首个带中继的版本（v0.18.0）装好后，仍须重连一次各宿主；之后的升级不再需要。
- 一键升级会联网，从 GitHub 拉取本仓库对应 tag 并改写 uv 工具目录。只在用户点击后执行，不会自动运行。
