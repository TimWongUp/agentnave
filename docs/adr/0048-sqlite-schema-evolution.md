# ADR-0048：SQLite schema 演进与迁移归属

- 状态：已接受
- 日期：2026-11-03
- 修订 [ADR-0026](0026-sqlite-conversation-store.md)：明确版本号规则与迁移由谁执行。
- 修订 [ADR-0033](0033-boss-workspace-handover.md)：取代「加列不升 `user_version`，托盘与服务各自补表补列」的做法。

会话库的 schema 每次变化都必须提升 `PRAGMA user_version`，并在一个事务内完成迁移。迁移只由服务执行：服务打开旧版本的库时先迁移，再提供服务。托盘只接受当前版本；遇到旧版本的库时只读展示，删除、交接、改名等写操作都提示用户先重连宿主，让服务完成升级。

1.0 把版本号从 1 升到 2。服务打开 v1 库时，先补齐 `workspaces`、`former_bosses` 两张表以及 `title`、`cwd` 两列，再按 [ADR-0050](0050-v1-compatibility-baseline.md) 删除旧身份会话，最后写入版本 2。此后打开库时不再探测表或列。

## 考虑过的方案

- **继续按列探测做兼容，版本号一直不变**（ADR-0033 原做法）：不用迁移，但服务和托盘每次打开库都要探测一遍，两边也都得写一份补表补列的代码，托盘因此会改写服务库的 schema，越过了自己的写入范围。
- **托盘也可以迁移**：没有服务时托盘也能直接处理旧库，但迁移规则要在 Python 和 Rust 里各维护一份。旧库只会在升级后、宿主重连前短暂出现，为这段窗口付出双份实现不划算，因此不采用。

## 后果

迁移完成后，仍在运行的旧版服务打不开新库，相关调用会报错，直到宿主重连。这个窗口与 [ADR-0047](0047-versioned-service-install.md) 的生效时机是同一段，托盘会在这段时间提示重连。
