# 安装改进与宿主反馈记录

记录日期：2026-09-08。安装说明、源归档内容检查、原生活动快照、可选总时限与任务交接指引已实现并完成本地验收。用户授权推送、审查及合并；本次不发布版本，也不替换各宿主使用的已安装运行时。

## 已同意的安装改进

继续使用 `uv tool`、稳定启动器和宿主原生注册方式，第一轮完善安装指南与相关发布内容检查。

1. 补齐各端安装说明。区分 WorkBuddy 桌面端与 CodeBuddy CLI 的有效配置入口，补充 Hermes 的交互式工具启用；注明 Skill 目录、验证方式、重启要求及实测宿主版本。机器专用路径不得成为公共安装要求。
2. 将现有复用规则整理为清晰主流程。分别检查运行时、MCP 注册和 Skill：相同则复用，缺失则补齐，不同则解释差异并保留用户选择，升级单独处理。交付区分新增、复用、修改和待验证。
3. 下一次正式发布让同一 tag 包含运行时源码、完整 Skill 及五份 CLI 参考文件。增加与实际安装来源一致的发布内容检查，复用现有 wheel 安装和 MCP 工具发现检查。版本发布需要另行执行完整发布任务；本记录不触发发布。
4. 分开报告配置检查、协议检查、真实宿主新会话加载和实际 Provider 调用。实际调用仍遵守配额授权要求，不把配置文件或独立 MCP 客户端检查当作所有宿主的端到端验收。

验收应覆盖已有安装的复用、缺项补齐、其他配置保留、Skill 引用完整性以及改动后的实际宿主入口。先利用现有检查，确有保护缺口再补最低成本验证。

## 已同意的运行状态与超时调整

- 扩展现有 `wait_agent` 的运行快照，消费已接入的原生事件流，向 Manager 提供有来源的近期活动、工具执行状态、简短进展、CLI 明确报告的重试或交互等待，以及事件时间。未提供的状态保持未知，不把沉默时间等同于卡死。
- Manager 根据证据决定继续等待或调用 `cancel_agent`；AgentNave 不增加自主终止判定、调度、通知或任务重试策略。
- 将默认 30 分钟硬截止改为调用方显式选择的可选总预算；未指定时不设 AgentNave 总运行截止。显式预算到期仍停止调用。单轮等待超时继续只返回 running，不停止任务。
- Provider 自身的超时独立核验，不静默修改原生设置；增加运行快照不能保证 Provider 没有其他截止限制。
- 已同步请求/快照合同、架构说明、Skill 和必要测试。快照保留原生状态与观察年龄，工具调用 ID 用于关联，不推断所有并发工作的完整状态。

## 临时产物与回答结构

用户保留临时目录要求，并撤回强制生成 Markdown 的方向。不要求统一生成结果文件，也不为了临时目录约束而新增落盘、预览截断或文件引用协议。

- AgentNave 自身产生的中间文件统一进入系统临时目录，不散落到调用方 cwd、项目仓库或安装目录。使用系统标准临时目录能力，隔离不同调用并限定本用户访问；能用内存或管道完成的内容继续不落盘。
- 本轮代码核验：目前只有 Grok prompt 通过 `tempfile.mkstemp` 写入系统临时文件，在调用清理时删除；其他适配器通过 stdin 传入 prompt，结果在内存中归一化。临时目录改进应复用这套能力，仅补真实缺口。
- 临时输入用完清理；如某任务明确需要供调用方读取的临时文件，应明确其可读生命周期，不能在返回路径前删除。当前不因此新增结果文件保留机制。
- 用户授权的正式代码改动和最终交付仍写目标位置；Provider 自己管理的认证、历史和缓存不被迁移或清理。Manager 可以要求子 CLI 将任务临时文件放到指定临时目录，但这属于指引，不是文件系统隔离保证。
- 没有统一的回答正文模板。Skill 要求 Manager 按下节准备任务和交接，正文格式按用户要求与任务需要指定；Adapter 不静默增加格式指令。
- MCP 的结构化终态字段与 CLI 回答正文是两层合同：外层保留状态、Provider、输出、会话 ID、费用、耗时和错误；`output` 内的正文结构由用户要求和 Manager 的任务 prompt 决定。JSON/事件流启动参数服务于协议解析，不要求模型正文必须输出 JSON 或 Markdown。

## 已修改的任务交接指引

用户要求借鉴 `handoff` Skill，用于主 Agent 向 CLI 派发任务或交接。已将相应用法加入本地 [agentnave-manager](../../skills/agentnave-manager/SKILL.md)：任务与范围、当前状态与下一步、已有产物引用、建议技能、敏感信息去除，以及长交接文档的临时目录与读取生命周期。简单任务内联，同一会话续接只补充变化，切换 CLI 或新会话重新提供必要上下文。具体规则以该 Skill 为唯一维护入口；不引入运行时 prompt 增补或私人 Skill 路径依赖。此项为本地变更，未发布。

## 本轮证据与限制

- 用户提供 Antigravity 和 WorkBuddy 的对话截图及 WorkBuddy 可访问性正文；两端均自述 Grok 调用一次成功，分别约 192 秒和 187 秒。WorkBuddy 自述成本为 0.296 美元。这些是原始宿主反馈；本轮另行执行了下述独立验收，未把截图中的耗时/价格作为性能基准。
- 本机安装收据指向 v0.5.0；已直接读取该安装的 `mcp_server.py`，并与当前仓库代码比较。Skill 入口指向当前仓库开发目录；两者不是同一发布版本的配套安装。
- 已核验当前 Skill 正文、`InvocationManager.wait`、MCP schema、结果序列化以及 WorkBuddy 配置中的延迟加载字段；未复制凭据值。
- 此前安装检查已确认 WorkBuddy CLI 写入 `.workbuddy/.mcp.json`，桌面程序的自定义 MCP 路径为 `.workbuddy/mcp.json`。这是当时本机版本的证据，公共安装指南应注明适用版本并保留重新核验步骤。

## 两端反馈核验

| 反馈 | 核验结论 | 后续处理 |
| --- | --- | --- |
| 延迟加载使调用多一步 | 两端均报告首次发现 schema 的额外操作。延迟工具发现由宿主控制，不能认定每次调用都必须重新发现。当前 Skill 已要求以实时 schema 为准，但没有专门说明延迟工具发现。 | 可补充通用说明：按 AgentNave 或精确工具名发现，复用当前上下文已有 schema；不统一修改各宿主延迟加载设置。 |
| 120 秒后 running，需要再次等待；单轮最多 300 秒 | 300 秒上限属实。`InvocationManager.wait` 等待同一个任务，完成即返回；到期才返回 running，属于有界长等待。当前 Skill 明确要求继续等待同一 ID，只说无需额外 sleep，没有禁止调用 `wait_agent`。 | 澄清长等待与短间隔主动查询的区别。缺少回调是当前接口边界；本次反馈不足以支持新增调度、通知或跨进程持久化。 |
| `describe_provider` 与 Skill 重复 | v0.5.0 确实仍返回 `defaults` 和 `guidance`；当前仓库已移除这两项。当前职责为宿主允许状态与支持参数，Skill 保存模型选择指引，不能互相替代。首次读取后可在当前上下文复用。 | 纳入后续配套发布与升级说明，避免把本机旧运行时体验误判成当前代码尚未处理的问题。暂不删除该工具。 |
| Antigravity 将约 15 KB 结果转存临时文件，需要再次读取 | 截图报告的是宿主的长工具结果处理。尚未核验原始 JSON、宿主阈值和是否存在重复载荷，不能据此认定 AgentNave 丢失结果。 | 保留待测。用户已撤回强制 Markdown 方向；不因此改变结果返回合同或引入持久存储、分页。 |
| 成本与延迟不透明 | 终态已有 `duration_ms` 和 `provider_usage`；其中费用只能保留 Provider 实际报告的值。单次约三分钟的总耗时不能证明是适配层开销，单次成本也不是固定价格或预测。 | 可在调用结果解读中提示读取这些字段，缺失时说明未报告；有性能疑点再分解耗时，不新增价格估算系统。 |
| WorkBuddy 其他 MCP 常驻占用上下文 | 本机 `tim-location`、`amap-maps`、`codegraph`、`keepygaga_rag` 显式为 `defer_loading: false`；AgentNave 未显式设置该字段。原反馈先说“所有”，随后列例外，表述不准确。实际常驻工具数量与 token 消耗未测量。 | 属于宿主配置的独立议题，不作为 AgentNave 安装的附带变更。 |
| CodeBuddy 被排除，因此本机不能调用 | 排除项作用于这一个宿主启动的 MCP 进程，符合当前同产品排除规则；不是整台机器禁用 CodeBuddy。其他允许该 Provider 的宿主仍可发起调用，实际可用性另需安装和认证条件。 | 在安装和故障说明中讲清作用域，不自动解除排除。 |
| 高德凭据出现在 URL | 与 AgentNave 项目缺陷无直接关系。配置含凭据不等于已证明外泄，也不能从截图断定所有日志均记录了凭据。 | 独立核验共享与日志暴露范围；本轮不复制凭据、不轮换密钥、不修改其他服务。 |

## 实施验收与剩余限制

通过开发运行时的真实 STDIO MCP 连接分别调用五个 Provider，任务仅执行一次短暂等待与 `pwd`，没有改项目文件：

| Provider | 实测结果 | 快照证据 |
| --- | --- | --- |
| Claude | 明确认证失败重试后由调用方取消，约 5 秒 | `system.api_retry` / `authentication_failed`；先前显式 180 秒预算验收也返回 `timed_out` |
| CodeBuddy | 成功，约 15 秒，cwd 正确 | `Bash` started / completed |
| Grok | 成功，约 15 秒，cwd 正确 | `run_terminal_command` in_progress / completed |
| Codex | 成功，约 32 秒，cwd 正确 | `command_execution` in_progress / completed |
| Antigravity | 成功，约 51 秒，cwd 正确 | `run_command` ACTIVE / DONE |

这些测试验证了 AgentNave 与真实 CLI 的协议、活动及工作目录传递；没有把独立 MCP 客户端验收冒充所有桌面端新会话加载验收。Claude 的认证状态属于外部环境，本次没有修改认证，也没有宣称 Claude 业务任务成功。

临时文件要求复用已有标准库机制，没有新增统一结果落盘。长结果的宿主转存行为仍待单独复现；回调、跨重启持久化、分页和统一宿主配置管理不在本轮范围内。
