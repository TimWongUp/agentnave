# 简报模板与插话引导

首次派发、续接、评审、整改或插话引导运行中任务时读本文。用不上的行删掉，不留占位；服务已自动要求回报未满足要求、未验证范围、阻塞与待决定事项，无需再手抄固定三行模板。

## 简报模板

**首次派发或交接**

```text
目标：<要做什么>
验收：<怎样算完成>
返回：<要包含和不必包含的内容、格式、产物位置>
范围：<目录和可改的文件>；保留：<不能动的改动>；授权：<能做到哪一步>
材料：<规格、ADR、Issue、diff 的绝对路径或 URL，注明用途>
已知：<已核实的进展和验证、已定决策及理由、试过并放弃的做法、阻塞>
待判断：<要执行者自己判断的事>
待办：<未完成项和下一步>
技能：<直接相关的 Skill 和已知路径>
```

**续接同一线程**

```text
上次之后：<新信息或 boss 的决定>
这次要做：<下一步>
返回：<要包含和不必包含的内容、格式>
```

**评审**（工位和失败假设按 `agentnave-review`）

```text
候选：head <完整 SHA>，base <完整 SHA>，git diff <base>...<head>
失败假设：<这个工位负责的假设>
证据边界：<规格、ADR、PR 的路径或 URL>
角色要点：<reviewers.md 对应段落>
返回：每条 finding 写位置、缺陷、失败场景、严重度、证据类别；结尾说明有无实质 finding、未审范围与待决定事项；不复述代码和规格原文
```

**整改**（续接实现者；各评审结论用 `forward` 按顺序传入）

```text
处理：<按本次转发的 #1、#2 写：要修的项；不修的项及理由>
验证：<要运行的检查>
返回：改了什么、检查结果及未完成项
```

无法使用 `forward` 时，才在 `处理：` 前补写每条的位置与失败场景。

## 返回内容边界

「返回」用内容边界控制回复，不靠字数，按任务类型写明要包含和不必包含什么：

- **探索、调查**：结论先行；每条结论附 `文件:行` 或出处，标明已核实还是推测；不贴大段代码或日志。
- **实现、整改**：改了什么、理由、运行的检查及结果、未完成项；不贴代码或 diff。
- **调研、素材收集**：字段按任务定，说明出处和未核实范围。
- **长报告、日志或附件**：让 CLI 保存到约定位置，回复摘要和绝对路径，boss 需要时再读。每次调用保留的标准输出上限 1 MiB、stderr 64 KiB，超限报 `output_limit_exceeded` 并终止。

## 插话引导

运行中的任务不能追加消息。要补充信息、纠正方向或改要求时，先打断再续接同一线程：原生会话的上下文都还在，效果等同插话。

- **何时插话**：用户给了新要求，或从 `wait(wait_seconds=0)` 的输出尾部、阶段性产物看出方向错了，继续跑会白费工作或写出要返工的改动。补充不影响当前这一步时，等它结束再续接，不打断。回答弹框用 `answer_prompt`，不算插话。
- **怎么插话**：`cancel` 该任务的 `invocation_id`，用回执里的 `session_id` 续接（回执没有时用 `read_conversation` 读回；仍然没有就按首次交接重写，写明已有进展），非工位任务重新声明 `access`。会议席位的插话见[会话与审核](studio.md)。续接时不复述原任务，只写这次的引导：

```text
插话：上一轮被我打断，原任务和上下文仍然有效。
引导：<新信息、纠正或改动后的要求>
先做：核对已执行的命令和改动的现状，不重跑；与引导不冲突的进展保留
返回：先交出打断前的结论和进展，再按引导继续
```

打断不撤销已执行的命令和写入，写任务被打断后由续接的员工核对工作区，boss 验收时也要看实际改动。换 CLI 或开新线程时重新交接，不假定旧历史可见。
