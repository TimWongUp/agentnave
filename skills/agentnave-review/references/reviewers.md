# 评审角色

## 通用 brief

评审工位不继承主对话。每个 prompt 按 `agentnave-manager` 的"目录与交接"提供必要内容，并写明：

- `cwd` 为候选所在仓库根目录；head、base 的完整 SHA 和 diff 命令 `git diff <base>...<head>`。
- 本工位唯一的失败假设和证据边界；超出边界只在影响该假设时提及。
- 可用的规格、验收标准、ADR、Issue 或 PR 绝对路径／URL；CLI 原生加载项目规则，需要补读局部规则时点名。
- 按下方格式返回，并给出回复长度预算。

复核时续接同一工位，只补原 finding、新 head 和整改证据。

## Finding 格式

每条 finding 包含：

- 位置：`file:line`
- 一句话缺陷
- 失败场景：具体输入或状态 → 错误输出、崩溃或代价
- 严重度：高、中、低
- 证据类别：代码、规格、仓库规范或判断；判断类注明属于判断

结尾说明是否有实质 finding 以及未审范围。没有就直说，不凑数；已由当前通过的工具链完整覆盖的检查不重复。

## 角色

| 角色                        | 何时派                   | 组员   |
| --------------------------- | ------------------------ | ------ |
| `correctness-reviewer`      | R1–R3 必派               | 常规   |
| `architecture-reviewer`     | 职责、耦合、公开接口风险 | 高推理 |
| `security-reviewer`         | 跨信任边界的数据流、授权 | 高推理 |
| `performance-reviewer`      | 热路径、规模、资源       | 常规   |
| `test-reliability-reviewer` | 测试能否保护目标行为     | 常规   |
| `simplicity-reviewer`       | 有实质的多余复杂度       | 高推理 |
| `specialist-reviewer`       | 其他明确低频专业         | 常规   |
| `adversarial-verifier`      | R3 整改后反证            | 高推理 |

### correctness-reviewer

找具体的错误行为、回归、边界失败、错误处理缺口和契约不符。逐项过一遍以下角度，各角度结论互不压制：

- **逐行**：读每个 hunk，再读它所在的整个函数；被改函数里未改动的行也在范围内。每行问：什么输入、状态、时序或平台会让它出错。
- **被删行为**：每处删除或替换的行原本保证什么不变量，新代码在哪里重新保证；找不到就是候选（删掉的守卫、丢失的错误路径、收窄的校验、删掉的有效测试）。
- **调用方追踪**：被改函数的调用方是否因新前置条件、返回形状、新异常或时序依赖而出错；同一改动里的其他变化是否让被调方变得不安全。
- **语言陷阱**：所用语言和框架的经典坑，如假值零、可变默认参数、闭包捕获循环变量、时区与浮点比较。
- **包装转发**：新增或修改的缓存、代理、装饰器、适配器是否把每个方法转给被包装对象，而不是绕回注册表或全局。
- **对照规格**：漏实现、半实现、未要求却改变契约的行为、字面符合但行为不符。
- **收尾补漏**：带着已列清单再读一遍 diff，只找遗漏：搬移代码时丢了守卫或锚点、配置默认值翻转、锁范围缩小、带副作用的判断方法、测试 setup／teardown 不对称。

### architecture-reviewer

找职责错位、隐藏耦合、重复的权威来源、可避免的复杂度、脆弱扩展点和公开接口风险。缺少当前需求支撑的抽象、参数或钩子，只有在实质增加耦合或演进风险时才报。给出严重度、位置、风险和最小可行方向。

### security-reviewer

沿真实数据流追踪跨信任边界的路径。每条 finding 写明攻击前提、触发路径、影响和证据位置；没有可行路径的理论可能不升级为漏洞。

### performance-reviewer

报告有具体触发条件和实际影响的风险：复杂度、重复 I/O、查询放大、内存增长、争用、高频分配、热路径变化。优先依据代码证据、规模假设或测量；一般可维护性建议不归为性能问题。

### test-reliability-reviewer

检查测试是否覆盖实质行为、断言是否验证结果、隔离和确定性是否可信、失败路径是否有回归保护。每个新增或保留的测试要以保护当前行为、可信失败路径、边界或回归来换取维护成本；追覆盖率、复制生产逻辑、绑定实现细节、昂贵又无独特保护的测试是删除或合并候选，前提是等价保护仍在。

### simplicity-reviewer

按顺序检查，前一项已满足当前契约就停：

1. 删除没有当前需求、调用方或实际效果的代码、配置、兼容逻辑和预留脚手架。
2. 复用仓库已有代码或模式、标准库、平台能力或已有依赖。
3. 合并单实现接口、单调用方转发层、重复 helper 或状态、散在调用方的等价补丁。
4. 缩减缺少当前契约、真实信任边界、具体风险或测量依据的哈希、缓存、重试、兼容处理、额外状态和重复校验。
5. 缩减没有独立行为保护的测试，以及为单次改动引入的测试基础设施。

每条写明位置、类别（删除、复用、合并、防御、测试）、为何多余、保持等价行为的最小替代和保留的保护。真实信任边界的校验、安全与数据完整性、防数据丢失、无障碍、用户明确要求、仓库门禁和有独立回归价值的测试一律保留。个人风格、行数、文件数本身不构成 finding；按预期缩减量排序。

### specialist-reviewer

brief 中写明一个专业领域和一个风险。按该领域标准检查真实失败路径、不变量、边界和集成影响，写明领域依据；跨领域影响只在解释该风险时提及。

### adversarial-verifier

brief 中给出已接受的结论、整改 diff 和验证证据。尝试推翻结论：绕过输入、状态组合、调用顺序、集成边界和隐含假设。找到反例时写明路径、影响和可复现证据；找不到时说明结论未被推翻并列出剩余不确定性。不重复做一般评审。
