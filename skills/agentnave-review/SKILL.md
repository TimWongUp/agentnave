# AgentNave 评审门控

本 Skill 规定评审分级、工位选择、裁决与留记录；派发、等待、续接和交接的调用方式按 `agentnave-manager`。boss（宿主里的主 Agent）负责固定候选、裁决、整改和最终结论，评审工位的报告只是假设。

## 授权

- 执行评审时，R1–R3 可派只读评审工位，无需用户点名 CLI；每个工位都消耗配额，按风险派，不凑人数。让评审工位直接修改代码仍须用户明确指定；编排偏好授权的实现分工不在此列。
- 评审角色的 `access` 由服务补为 `read`，并给 prompt 加只读说明，都不用写；`native=true` 的工位由宿主自带子代理执行，不经过服务，要在 prompt 写明只读（不改文件、不提交、不推送、不发评论）和非交互。声明只是约定，只读靠 Provider 原生权限；不自行追加权限类参数。

## 步骤

### 1. 固定候选

候选须已提交。取目标分支与候选 head 的合并基作 base，评审范围是 `git diff <base>...<head>` 的完整 diff。无法固定边界时报告阻塞，不声称评审完成。

完成标准：记下 head 与 base 的完整 SHA 和 diff 命令。

### 2. 定级

先列出这次改动未排除的**失败假设**（什么输入或状态下会出什么错），再取最高匹配等级。相邻等级无法区分时取更高；都不完全符合又没有明确 R2 条件时按 R2。

| 等级 | 条件                                                                                                                                                             | 评审工位                                                                         |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| R0   | 局部、自包含，boss 能在最终可观察边界完整验证，容易发现和恢复，没有未排除的失败假设；不改依赖、构建／部署、公开契约、测试语义或安全策略                          | 无；boss 按 [评审角色](references/reviewers.md) 的正确性方法自查完整 diff 并验证 |
| R1   | 局部、可恢复、已有相关验证，恰有一个失败假设，独立判断可能改变结论                                                                                               | `correctness-reviewer`；该假设属明确专家领域时再加对应专家                       |
| R2   | 两个及以上独立风险维度；或改变广泛、难恢复的公开契约；或触及安全、隐私、并发、数据兼容、部署等敏感边界                                                           | `correctness-reviewer`，每个独立风险各加一个匹配专家                             |
| R3   | 定义或削弱信任／授权边界；失败可能造成未授权访问、代码执行、密钥泄露、不可逆数据丢失、财务影响、供应链破坏或广泛生产中断；或评审中发现会改变原风险假设的实质缺陷 | 同 R2 并聚焦专家；整改验证后加 `adversarial-verifier`                            |

风险维度包括正确性、架构、公开契约、安全、隐私、并发、状态、数据兼容、迁移、测试可靠性、性能、资源、部署和供应链。依据是失败假设，不是文件数、行数或期望人数。同一失败假设最多一个专家。

完成标准：一个等级、一句理由、失败假设清单及每个假设的负责工位。

### 3. 派评审

读 [评审角色](references/reviewers.md)，按其中的通用 brief 和角色要点为每个工位写 prompt，每个工位只领一个失败假设和证据边界。

- 用 `start_agent` 私聊派发，互不可见，结果只回到 boss；多个工位并行派出，一起等待。
- 按下方"选工位"为每个角色定工位，prompt 用 `agentnave-manager` 的评审模板。
- `role` 用角色名（如 `correctness-reviewer`），同一角色在后续复核中续接自己的线程。
- 评审期间并行跑相关 CI 和本地验证。

完成标准：每个已分配的失败假设都有终态报告，或记下缺席及处理（重派、换组员或降级）。

#### 选工位

按顺序取第一个适用的来源：

1. **本次点名**：用户在当前对话里指定的 CLI、模型或档位。指明角色时只对该角色生效，否则对全部工位生效；只给 CLI 时用其 App 组员默认模型。本次评审的复核和反证沿用。点名的工位用不了时报告原因并询问用户，不擅自替换。
2. **App 评审工位**：`list_members` 回执的 `review`，按角色给出用户在 AgentNave App 里选的 `provider`、`model` 和 `effort`。派发时传 `role`，服务按工位选 CLI 并套用模型和档位，不必再传；续接只传 `session_id`；核对回执 `defaults_applied` 以该角色的 seat 开头。`native=true` 表示该 CLI 与宿主同类：改用宿主自带的只读子代理，宿主允许指定模型时用同一模型。`available=false` 时看 `reason` 和 `replacement`：`replacement` 给出可直接传的 `provider`、`provider_options` 和原因，连同 `role` 一起传，服务不会自动换，由 boss 决定用不用；没有 `replacement` 或不合适时按第 3 项自动选。
3. **自动**：按 `list_members` 选，优先与改动作者不同的模型，高推理角色（见评审角色表）用最强可用组员。

每个工位的来源（点名、App 评审工位、替换及原因、自动）写入记录。

### 4. 裁决

逐条核对 finding 与固定候选和引用证据，给出一个判定：

- **CONFIRMED**：能指出触发它的输入或状态及错误结果，并引用对应行。
- **PLAUSIBLE**：机制成立，触发条件不确定（时序、环境、配置）；写明什么能证实它。
- **REFUTED**：只有能从代码构造出反证时才判：引用行证明说法不符、类型／常量／不变量使其不可能、本次 diff 已有守卫，或纯风格且无可观察影响。

状态现实可达时（并发竞态、罕见但可达路径上的空值、未排除边界的差一错误、部分失败与重试），"推测性"或"依赖运行时状态"都不是驳回理由，按 PLAUSIBLE 处理。CONFIRMED 与 PLAUSIBLE 视为接受。多数票不是判定规则；报告冲突时比较证据质量、范围和可复现性。

完成标准：每条 finding 都有判定和处理：修复、不修并说明理由，或交用户决定。

### 5. 整改与复核

在已有授权内整改并运行受影响的验证。复核续接原评审工位（同组员同 `role`），附原 finding、新 head 和整改证据，只要求定向复核，不重跑完整评审；原工位不可用时开同角色新工位并附同样材料。整改或复核发现改变了原风险假设时回到第 2 步重新定级。

### 6. R3 反证

R3 在聚焦评审、整改和验证之后，派 `adversarial-verifier`（宜换一个模型）尝试推翻已接受的结论。未解决的反例阻止评审通过。

### 7. 记录

评审完成后留一条记录：

- 评审的 head 与 base
- 等级及理由
- 实际评审工位（provider、model、role、来源）与各自覆盖的失败假设
- findings、判定、处理结果和未解决项
- 本地验证与 CI 状态
- 剩余风险

有 PR 时发为 PR 评论；没有 PR 时写入任务交接。合并或接手前据此复核。

## CI

评审不依赖是否配置 CI。有相关 CI 时等待终态并处理失败，依赖 CI 的结论须等终态；没有 CI 时运行适用的本地验证并说明覆盖缺口。CI 待批准、未产生运行或无法启动都是阻塞，不算"无 CI"或通过。不为满足评审新建 CI。

## 候选变化与复用

只有 head／base、风险覆盖、findings 和验证证据都仍适用时才复用先前评审。head 或 base 变化后检查新增 diff 和集成影响，重新定级，只补受影响的风险和验证；无关变化不抹除仍有效的证据，然后补一条新记录。

## 降级

AgentNave 不可用、宿主连接缺少所需工具或所有可选组员都失败时，改用宿主自带的只读子代理并在记录中注明。两者都不可用时，R1–R3 报告阻塞：boss 自查不算独立评审。
