# AgentNave 评审门控

本 Skill 规定评审分级、工位选择、裁决与记录内容；何时评审、是否开 PR、记录发到哪里按用户或项目规则，本 Skill 不另规定。派发、等待、续接和交接的调用方式按 `agentnave-manager`。boss（宿主里的主 Agent）负责固定候选、裁决、整改和最终结论，评审工位的报告只是假设。

## 授权

- 执行评审时，R1–R3 可派只读评审工位，无需用户点名 CLI；每个工位都消耗配额，按风险派，不凑人数。让评审工位直接修改代码仍须用户明确指定；编排偏好授权的实现分工不在此列。
- 只读声明、`native` 工位和权限类参数按 `agentnave-manager`。
- 只开会档（规则块写明只用会议室，宿主装的是 `agentnave-meeting` 而不是 `agentnave-manager`）不私聊派评审工位：告诉用户在 AgentNave App 把编排切到其他档再评审，或由用户决定改在会议室里讨论。

## 步骤

### 1. 固定候选

候选须已提交。取目标分支与候选 head 的合并基作 base，评审范围是 `git diff <base>...<head>` 的完整 diff。无法固定边界时报告阻塞，不声称评审完成。候选落后于目标分支时，本地检查跑在它和最新目标分支的合并结果上，可用临时合并。

完成标准：记下 head 与 base 的完整 SHA 和 diff 命令。

### 2. 定级

先列出这次改动未排除的**失败假设**（什么输入或状态下会出什么错），再取最高匹配等级。相邻等级无法区分时取更高；都不完全符合又没有明确 R2 条件时按 R2。

| 等级 | 条件                                                                                                                                                             | 评审工位                                                                         |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| R0   | 局部、自包含，boss 能在最终可观察边界完整验证，容易发现和恢复，没有未排除的失败假设；不改依赖、构建／部署、公开契约、测试语义或安全策略                          | 无；boss 按 [评审角色](references/reviewers.md) 的正确性方法自查完整 diff 并验证 |
| R1   | 局部、可恢复、已有相关验证，恰有一个失败假设，独立判断可能改变结论                                                                                               | `correctness-reviewer`，App 设了 `correctness-reviewer-easy` 时用它；该假设属明确专家领域时再加对应专家                       |
| R2   | 两个及以上独立风险维度；或改变广泛、难恢复的公开契约；或实质改变安全、隐私、并发、数据兼容、部署等敏感边界                                                           | `correctness-reviewer`，再按专业加专家，相关风险合给同一专家                             |
| R3   | 定义或削弱信任／授权边界；失败可能造成未授权访问、代码执行、密钥泄露、不可逆数据丢失、财务影响、供应链破坏或广泛生产中断 | 同 R2 并聚焦专家；整改验证后加 `adversarial-verifier`                            |

风险维度包括正确性、架构、公开契约、安全、隐私、并发、状态、数据兼容、迁移、测试可靠性、性能、资源、部署和供应链。依据是失败假设，不是文件数、行数或期望人数。同一失败假设最多一个专家；新增专家要说明已派工位覆盖不了什么。

完成标准：一个等级、一句理由、失败假设清单及每个假设的负责工位。

### 3. 派评审

读 [评审角色](references/reviewers.md)，按其中的通用 brief 和角色要点为每个工位写 prompt。`correctness-reviewer` 看完整 diff，失败假设只是重点，清单外的问题同样要报；专家领同一专业的一个或多个假设和证据边界。

- 用 `start_agent` 私聊派发，互不可见，结果只回到 boss；多个工位并行派出，一起等待。
- 按下方"选工位"为每个角色定工位，prompt 用 `agentnave-manager` 的评审模板。
- `role` 用角色名（如 `correctness-reviewer`），同一角色在后续复核中续接自己的线程。
- 派发前先过静态检查和已知失败的测试，耗时测试和 CI 与评审并行。

完成标准：每个已分配的失败假设都有终态报告，或记下缺席及处理（重派、换组员或降级）。

#### 选工位

按顺序取第一个适用的来源：

1. **本次点名**：用户在当前对话里指定的 CLI、模型或档位。指明角色时只对该角色生效，否则对全部工位生效；只给 CLI 时用其 App 组员默认模型。本次评审的复核和反证沿用。点名的工位用不了时报告原因并询问用户，不擅自替换。
2. **App 评审工位**：直接按角色名传 `role` 派发，不先查 `list_members`；服务按工位选 CLI 并套用模型和档位，续接只传 `session_id`；核对回执 `defaults_applied` 以该角色的 seat 开头。服务按用户在 App 配置的备选顺位取第一个可用，回执 `seat_fallback` 表示用了备选，同属 App 评审工位来源，记录里注明所用模型即可，不算替换。落在宿主同类工位时回执为 `status="not_started"`、`reason="native_seat"`，按其中的模型和档位交给宿主自带子代理，也注明这个来源。工位未配置或全部顺位都不可用时报错：`available=false` 表示后者，`replacement` 按 `agentnave-manager`，服务不会采用，没有或不合适时按第 3 项；工位未配置时直接按第 3 项，第 3 项才查 `list_members` 的 `members`。
3. **自动**：按 `agentnave-manager` 从 `members` 选，优先与改动作者不同的模型，高推理角色（见评审角色表）用最强可用组员。

来源不是 App 评审工位时（点名、替换及原因、自动）写入记录。

### 4. 裁决

逐条核对 finding 与固定候选和引用证据，给出一个判定：

- **CONFIRMED**：能指出触发它的输入或状态及错误结果，并引用对应行。
- **PLAUSIBLE**：机制成立，触发条件不确定（时序、环境、配置）；写明什么能证实它。
- **REFUTED**：只有能从代码构造出反证时才判：引用行证明说法不符、类型／常量／不变量使其不可能、本次 diff 已有守卫，或纯风格且无可观察影响。

状态现实可达时（并发竞态、罕见但可达路径上的空值、未排除边界的差一错误、部分失败与重试），"推测性"或"依赖运行时状态"都不是驳回理由，按 PLAUSIBLE 处理。CONFIRMED 与 PLAUSIBLE 视为接受。多数票不是判定规则；报告冲突时比较证据质量、范围和可复现性。

完成标准：每条 finding 都有判定和处理：修复、不修并说明理由，或交用户决定。

### 5. 整改与复核

在已有授权内整改并运行受影响的验证。复核续接原评审工位（同组员同 `role`），附原 finding、新 head 和整改证据，只要求定向复核，不重跑完整评审；原工位不可用时开同角色新工位并附同样材料。整改或复核发现改变了原风险假设时回到第 2 步重新定级。

R1–R3 由 boss 在无外部副作用的环境或隔离环境里，把最终候选的主路径实际跑一遍；真实安装和外部写入仍要授权，跑不了的写进剩余风险。

### 6. R3 反证

R3 在聚焦评审、整改和验证之后，派 `adversarial-verifier`（宜换一个模型）尝试推翻已接受的结论。未解决的反例阻止评审通过。

### 7. 记录

评审完成后写一条记录：

- 评审的 head 与 base
- 等级及理由
- 覆盖的失败假设，各注明评审模型
- findings、判定、处理结果和未解决项
- 本地验证（注明所在 head）与 CI 状态
- 剩余风险

记录发到哪里（如 PR 评论、文件）按用户或项目规则；没有规定时写在给用户的回复里。合并或接手前据此复核，合并绑定记录里的 head：GitHub 用 `gh pr merge --match-head-commit <head>`，其他平台合并前核对。

## CI

评审不依赖是否配置 CI。合并要等哪些 CI 按用户偏好，没有偏好时等全部相关 CI。要等的 CI 须到终态并处理失败，失败时对照 base 上同一 CI 分清本次引入和既有故障，既有故障写进剩余风险；依赖 CI 的结论同样要等；它待批准、未产生运行或无法启动都是阻塞，不算"无 CI"或通过。没有 CI 时运行适用的本地验证并说明覆盖缺口。不为满足评审新建 CI。

## 候选变化与复用

只有 head／base、风险覆盖、findings 和验证证据都仍适用时才复用先前评审。head 或 base 变化后检查新增 diff 和集成影响，重新定级，只补受影响的风险和验证；无关变化不抹除仍有效的证据，然后补一条新记录。

## 降级

AgentNave 不可用、宿主连接缺少所需工具或所有可选组员都失败时，改用宿主自带的只读子代理并在记录中注明。两者都不可用时，R1–R3 报告阻塞：boss 自查不算独立评审。
